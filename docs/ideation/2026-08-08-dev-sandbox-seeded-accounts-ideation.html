Grounding Context

PR #239 made make dev derive PACTO_TEST_SANDBOX_ROOT from the current git branch, so each branch gets its own test_fixtures/dev-branch-<slug>/. That fixed storage-format update-gate collisions from branch-hopping across different migrations, and created the problem this ideation addresses: every fresh branch sandbox boots to an empty account-creation screen with no squads, DMs, messages, wallet history, or governance state. Tracked as an open gap in issue #237.

The reframe that shaped this set

The naive framing — "fabricate fake rows into pacto.db" — is wrong, because a complete developer-controlled dev stack already exists in the sibling repo pacto-dev-env and was running on this machine during grounding (relay healthy on 127.0.0.1:7000, pacto-bot-api healthy, both up two days).

It already seeds a rich world: governance contracts, a full Nave Pirata squad, deterministic bot identities (captain, candidate, crew-1..3) with committed nsec values, and live relay state including DMs, KeyPackages, and MLS groups. It exposes make seed, make seed-squad, make create-mls-group BOT_ID=… RECIPIENT_NPUB=…, make publish-key-package, and make reseed-all.

So the counterparty half is solved; the protagonist half is not. There is no user identity the app can log in as, the app cannot reach the local relay anyway, and nothing carries npubs, group ids, or deployment addresses across the two-repo seam. Ideas were generated against that problem; anything reinventing bot peers, a local relay, or on-chain squad seeding was cut as duplicating shipped work.

Verified constraints the survivors are qualified against

  • The launch wall is network, not crypto. crypto.rs:39-41 states Argon2id was tuned to keep unlock "fast (~100ms)". The documented 20–30s wait is relay round-trips — an MLS keypackage publish plus a tail of fetch_events_from/stream_events_from calls with 5–15s timeouts. Why those timeouts elapse is unproven (see the rejection of the boot-reordering idea).
  • TRUSTED_RELAYS is a compile-time constant. lib.rs:115, roughly 30 call sites across lib.rs, mls.rs, commons.rs, squad_bot.rs. No env override, no local fallback.
  • Identity adoption already ships. importAccount(recoveryPhrase, pin) at src/stores/auth.ts:250, plus a raw-nsec backend primitive documented "nsec only" at src/lib/api/auth.ts:13-15. This is the single most important correction in the whole run — three independent frames nominated "make the app able to adopt an identity" as the big unlock, and it is already possible. Only its automation is missing.
  • process_rumor is public and relay-free (rumor.rs:125-128), so synthetic history can enter storage through the real ingest path with no network at all.
  • Committed fixture DBs are a live hazard. classify_database returns Unrecognized/Divergent for a profile the running build doesn't recognize, and the update gate then blocks every account on the machine. Orphan cleanup deliberately refuses to delete such profiles (account_manager.rs:352-382), so a stale fixture lingers as a launch-blocking landmine rather than disappearing.
  • Fixture DBs are cryptographically portable — plaintext salt plus deterministic Argon2id means a known dev PIN unlocks anywhere. Which also means a committed fixture leaks its own nsec and EVM key.
  • CI provisions zero fixture data across all four jobs.
  • Port 7000 is double-bound on macOS — Docker and ControlCenter (AirPlay Receiver) both hold it, verified live. Docs name ws://localhost:7000 in seven places while the working endpoint is the Caddy-fronted wss://localhost:7001.

Round two: pacto-bot-api enters scope

A third repo came into scope after the first round: ~/Projects/pacto-bot-api, a Rust daemon plus a pacto-bot-admin CLI that multiplexes bot identities over JSON-RPC, with a Python SDK for handlers. It is the substrate the dev stack's bot roster runs on, and it changes several answers.

  • Identity minting is a first-class command. pacto-bot-admin new <BOT_ID> (src/admin.rs:266-372) mints an identity and writes a config snippet, with --backend (nsec dev-only, bunker_local, bunker_remote), --capabilities, --relays, and --scaffold to generate a Python handler project with slash-command stubs and pytest files.
  • Capabilities are an explicit permission model (src/admin.rs:284-286): ReadMessages, SendMessages, ManageProfile, SendGroupMessages, ReceiveGroupMessages, CreateMlsGroup, InviteToMlsGroup, ExitMlsGroup — defaulting to read plus send.
  • There are composable history primitives already: send-test-dm <BOT> <RECIPIENT> <CONTENT>, mls-group create|invite|repair-admins, publish-profile (kind:0, so a persona can have a display name and avatar), and trace-events for reading back what a bot actually did.
  • MLS state has an export/import path. export <BOT> --bundle-dir DIR (admin.rs:1752-1826) copies the MLS store, its -wal/-shm/-journal sidecars, and its key into a 0o700 directory; import restores it and try_open_mls_store_with_key (admin.rs:1846) verifies the key opens the store before accepting it.
  • Crate parity is exact. Both repos resolve to mdk-core 0.8.0, mdk-sqlite-storage 0.8.0, nostr-sdk 0.44, and both call the same MdkSqliteStorage::new_with_key(path, EncryptionConfig::new(key)) (admin.rs:1850 / mls.rs:324-325). The MLS store schema is therefore identical across the two projects.
  • But key provenance differs. bot-api mints a raw random 32-byte key via getrandom into a .key sidecar (mls_key.rs:129-137); pacto-app derives its key from the user's PIN and per-device salt. Same EncryptionConfig type, structurally different secret.

The correction that matters

A first-pass review concluded "MLS group state cannot transfer to pacto-app via an nsec." That is true but answers the wrong question — it rules out transfer by identity while missing transfer by bundle, which bot-api explicitly supports and which crate parity makes viable.

The accurate verdict is narrower and more useful: MLS transfer is mechanically possible but protocol-hazardous. Two clients sharing one ratchet state fork and produce undecryptable messages — and bot-api knows it, stamping split_brain_warning: true on every single export (admin.rs:1606, field at 3860). It warns about a hazard it does not prevent. That gap, not the format question, is where the round-two design space lives — and it is why the strongest new idea below avoids transfer altogether.

Make TRUSTED_RELAYS configurable — and retire port 7000

Description: Replace the compile-time static TRUSTED_RELAYS: &[&str] with a list resolved at startup from an env var or dev config, defaulting to the same three public relays in release builds and overridable only in debug. Fold in the URL correction: retire ws://localhost:7000 — which macOS ControlCenter squats — in favour of the Caddy-fronted wss://localhost:7001, matching the wss:// scheme every existing entry already uses.

Axis
network-state
Basis
direct: lib.rs:115 — pub(crate) static TRUSTED_RELAYS: &[&str], with call sites confirmed across lib.rs, mls.rs, commons.rs, squad_bot.rs. src/lib/dev/local-dev-setup.ts:12 hardcodes const LOCAL_RELAY_URL = 'ws://localhost:7000' and only adds it to the user relay list, which does not govern MLS. Port collision on :7000 verified live against both Docker and macOS ControlCenter.
Rationale
Every MLS-dependent seeding approach is gated on this one constant — group creation, keypackage fetch, and welcome delivery all route through it. Until it is overridable, seeding is architecturally capped at whatever relay-free injection can fake. It also unlocks CI relay isolation, offline development, and per-run test isolation from the same change, because all four fail today for the identical reason.
Downsides
Touches ~30 call sites, and it moves a trust boundary — which relays the app believes. Needs a deliberate mechanism decision (env var vs config file vs build flag) and hard gating so a release build can never be pointed at an attacker-supplied relay. The bot roster already publishes to wss://jskitty.cat/nostr, which is in the default list, so a narrower interim path exists at the cost of pushing dev traffic onto a public relay.

One joint bootstrap command with readiness gates

Description: A single make dev-populated in pacto-app that drives the sibling stack's existing targets in order — up, seed, seed-squad, publish-key-package — waits on real readiness gates between stages, reads the resulting identity back out of pacto-bot-api.toml, and only then launches Tauri already pointed at the seeded world. Not new seeding logic: orchestration and a handoff format for what the stack already produces.

Axis
fixture-lifecycle
Basis
direct: Two repos with two make dev-shaped entry points and no documented joint workflow. The sibling stack already exposes the full command set (up, seed, seed-squad, create-mls-group, publish-key-package, reseed-all), and its ensure-sibling-repos target shows the authors anticipated cross-repo orchestration but only ever cloned pacto-gov — it never orchestrates pacto-app. external: staged bring-up with explicit readiness gates is standard practice in hardware-in-the-loop and test-executive frameworks, where independently-started subsystems otherwise race.
Rationale
The reframe names the seam as the actual open gap, and this is the idea that makes the seam disappear behind one invocation. Every other survivor is a component a developer would otherwise assemble by hand across two Makefiles and two READMEs.
Downsides
Creates a hard dependency from pacto-app onto a sibling repo's location, which needs an ownership decision (which repo hosts the orchestration, and what happens on a machine where the stack is absent). Must degrade gracefully to today's behaviour rather than breaking make dev for anyone without Docker.

A persona cast, not one hero account

Description: Treat the stack's existing bot roster as the canonical cast and expose named, swappable personas — make dev PERSONA=captain-with-treasury, crew-with-dm-backlog, candidate-mid-vote — where each persona atomically bundles an identity, its relay-published history, its EVM address, and its MLS memberships. Map pacto-app's existing dev-account / dev-buddy targets onto specific crew members so two windows can hold a genuine two-party conversation.

Axis
identity-bootstrap
Basis
direct: the stack defines per-bot capability sets and a crew roster via PACTO_SQUAD_CREW_BOT_IDS=crew-1,crew-2,candidate, with deterministic committed nsec values per bot. pacto-app's Makefile already carries dev-account and dev-buddy as persistent named identities — the names exist, the wiring to the roster does not. Verifier confirmed both halves are real.
Rationale
This answers the request literally: the ask was "a few predefined users", plural. It also converts UI states that are currently laborious to reach — a candidate mid-vote, a crew member with an unread DM backlog — into a flag, and makes genuine two-party DM and group testing possible instead of monologue-against-fixture-rows.
Downsides
Personas are a maintenance surface: each needs an owner and a script kept current, and the set will drift toward "whatever someone needed once". Worth capping at three or four deliberately chosen states. Depends on #1 or #2 to actually deliver the relay history a persona claims to have.

Two-tier db:seed, regenerated from code and reused by CI

Description: Promote the seeding machinery the repo already has — write_legacy_store_fixture, seed_pre_v28_schema, upsert_squad_inner, insert_entry — from private test-vector code into a supported seeding entry point that regenerates a migration-current database on demand. Two tiers: a relay-backed tier for fidelity, and a relay-free tier that constructs RumorEvents and calls process_rumor directly. Package the relay-free tier as a plain Rust library so Docker-less CI gets populated-state coverage for the first time.

Axis
local-state
Basis
direct: all four helpers verified to exist (mls_store_reset.rs:970, migrations/mod.rs:186, squad_catalog.rs:267, catch_up.rs:92), each private or test-only. process_rumor confirmed pub and relay-free at rumor.rs:125-128. CI confirmed to provision no fixture data in any job. external: Rails db:seed as a first-class, code-driven seeding command — the pattern external research found conspicuously absent from Nostr and E2E-messenger ecosystems.
Rationale
Regenerating from code is the one approach that structurally avoids the storage-format landmine: there is no stale artifact to become divergent because nothing is retained. The same investment then pays twice, since the generators double as backward-compatibility vectors for future migrations, and a third time when CI reuses the identical command.
Downsides
Promoting test-only code to a supported surface raises its maintenance obligation and blast radius. A new Tauri command needs a real frontend caller or it trips the documented orphaned-command failure — a standalone binary or library avoids that risk entirely and is probably the right shape. One correction to fold in: the MLS half of the relay-free tier is weaker than it first appeared — mls_keypackage_index is a doc-comment name, not a table (the real one is mls_keypackages, V1__initial_schema.sql:82), and the "prefer local index" text at mls.rs:425-440 sits inside a block comment, not executing code. Priming MLS state offline needs verification against mls.rs:507-527 before anyone commits to it.

Auto-import the Anvil deployment artifacts, with version pinning

Description: The stack already writes real local-chain addresses to full-system.json and squad.json; nothing reads them. Have the dev build import those artifacts at launch to populate the existing local (31337) chain entry and treasury addresses, deleting the manual Settings → EVM step. Stamp each deployment with an accession id that the app checks, so a mismatched or stale artifact refuses loudly instead of silently resolving wrong addresses.

Axis
on-chain
Basis
direct: wallet-assets.json carries a local (31337 → http://localhost:8545) entry with zero-address placeholders, verified verbatim; pacto-protocol-addresses.json holds only Sepolia; local-dev-setup.ts explicitly opts out of wiring EVM, leaving it a manual step. external: versioned reference assemblies in genomics (GRCh37/GRCh38), where tooling refuses to mix coordinate systems rather than silently producing wrong results.
Rationale
This is a fully populated artifact sitting on disk beside a config file with matching empty fields — an existing bridge with nobody walking across it. The pinning half matters because without it a future import has no way to detect that a squad.json came from an Anvil instance whose contracts no longer match the running build's ABI, which is precisely the silent-mismatch class the storage-format gate already refuses to tolerate elsewhere.
Downsides
Takes on a cross-repo dependency on an artifact format the other repo owns and can change. Needs defined behaviour when the artifact is absent, stale, or from a wiped chain. The accession scheme is only worth it if it is enforced — an unchecked version stamp is worse than none.

Fixtures that exercise the safety rails, not the happy path

Description: A second fixture target that deliberately seeds adversarial state rather than a plausible inbox: an Unrecognized-format profile sitting beside a valid one, orphaned rows with no matching event, and enough profiles to actually reach SCAN_DEADLINE. Pair it with a checksum over the resulting logical state so a regenerated fixture that silently diverges is caught as a desync rather than discovered later through an unrelated failure.

Axis
fixture-lifecycle
Basis
direct: AccountScanVerdict never returns Delete for an Unrecognized or Divergent profile — verified with dedicated regression tests at account_manager.rs:352-382,812-830 — and SCAN_DEADLINE is a real 5s bound at storage_format.rs:23 that no realistic local profile count has ever approached. external: lockstep and rollback netcode compute periodic state checksums precisely because replay divergence is silent and catastrophic otherwise.
Rationale
PR #239 exists because of storage-format collisions, and the safety code written in response has never been exercised by a fixture that actually triggers it. A realistic-looking populated user never runs those paths; only a deliberately hostile one does. This is the only survivor that is different in kind rather than degree, and it is the one that would have caught the bug class that started all of this.
Downsides
Serves testing rather than the daily developer-experience complaint that prompted the ask, so it competes for the same effort without making anyone's make dev nicer. The checksum half only earns its keep once fixtures are regenerated often enough to drift.

Zero-click dev login — automate the import flow that already ships

Description: Write the PIN-encrypted key, salt, and session marker into the sandbox's app-data directory before Tauri starts, so the auth state machine finds what it is looking for and lands authenticated with no create-account screen and no PIN entry. Where a new command is genuinely needed, the smaller change is letting test_login_fixture accept a supplied nsec instead of always generating a random one, and having it persist the key the way createAccount does.

Axis
identity-bootstrap
Basis
direct: checkAuthStatus (auth.ts:165-190) is a three-state machine gated on hasStoredKey() finding a PIN-encrypted key on disk; test_login_fixture (lib.rs:6091-6150) initialises backend state and an empty database but never persists that key, so the UI stays on the login screen. Argon2id is ~100ms per crypto.rs:39-41, so the PIN step is a UI gate, not a cost.
Rationale
Ranked last deliberately, and the reason is the most useful finding in this run. Three independent frames proposed this as the unlock, but identity adoption already ships: importAccount(recoveryPhrase, pin) at auth.ts:250 and a raw-nsec primitive at src/lib/api/auth.ts:13-15 both work today. So this is not new capability — it is automating a manual path that already exists. That still has real value, because it is the cheapest item here and the one every other survivor's inner loop sits on top of, but it should not be mistaken for the architectural gap.
Downsides
Bypassing the auth state machine on a build flag is a security-adjacent decision even when compile-gated out of release, and letting a debug command accept externally-supplied private keys widens that surface. Delivers little on its own: without #1 or #2 the developer lands authenticated into an account that is still empty.

8

Invite the developer, don't transfer the bot

Description: For the case that actually matters — a developer wanting to be a member of a squad that personas have already populated — move nothing. Run the already-shipped pacto-bot-admin mls-group invite --bot <ID> --group <GROUP> --recipient <DEV_NPUB> and let the developer's own pacto-app identity join as a genuinely separate MLS member. The bot stays live, the app derives its own ratchet state from a real Welcome message, and there is no shared key, no bundle, and no split brain — because nothing was copied.

Axis
network-state
Basis
direct: mls-group invite --bot --group --recipient exists today at src/admin.rs:605-618, alongside create with an explicit additive --admin set. The hazard it sidesteps is bot-api's own: every export payload is stamped split_brain_warning: true (admin.rs:1606). reasoned: MLS binds group membership to a client's own key material and ratchet state, so a Welcome-derived member is the protocol's intended way to add a participant. Copying a store makes two clients share one ratchet; inviting makes two members with two ratchets. Only the second is what MLS is designed to do.
Rationale
This is the only path in the entire design space that is hazard-free by construction rather than hazard-managed — every transfer-based idea exists to make copying safe, and this asks whether copying was ever the right default. It may also work before anything else on this list lands: the bots already publish to wss://jskitty.cat/nostr, which is in the app's default TRUSTED_RELAYS, so the Welcome can reach a stock debug build without idea #1. That makes it the natural first experiment — and the cheapest way to find out whether the rest of this list is even needed.
Downsides
Gives membership, not history: MLS forward secrecy means a newly-invited member cannot read messages sent before it joined, so "populated backlog" still needs bots to post after the invite (which is what idea #9 automates). Requires the developer's npub to exist first, so it composes with #7 rather than replacing it. Relying on the public relay as the interim transport pushes dev traffic onto shared infrastructure — acceptable briefly, not as the steady state.

Scenario files that compile to bot verbs, verified by trace-events

Description: Treat the bot fleet as a fixture-authoring language rather than a source of data to copy. A declarative scenario file names participants and a timeline — t+0 captain DMs the dev; t+5m captain creates group "council" and invites crew-1; t+10m crew-1 posts three messages; t+15m a poll opens — and a runner walks it, composing publish-profile, send-test-dm, and mls-group create|invite. Author it as one of the pytest files new --scaffold already generates, so the scenario is the SDK's own test and cannot drift from the SDK's API. Snapshot trace-events output as a golden file so CI catches the day a scenario silently stops producing what it claims.

Axis
fixture-lifecycle
Basis
direct: the primitives are stable and shell-composable today — send-test-dm <BOT> <RECIPIENT> <CONTENT> (admin.rs:435-444), mls-group create|invite (admin.rs:584-618), publish-profile (admin.rs:374-378), and trace-events --since --limit (admin.rs:450-461). new --scaffold generates a Python project with pytest by default, skippable via --no-tests (admin.rs:294-308). external: load-testing traffic generators and synthetic-monitoring canary users, where the generator is version-controlled alongside the system it exercises rather than maintained as a side script.
Rationale
This is what makes personas have a history rather than merely exist, and it closes the gap idea #8 leaves open — invitation grants membership, scenarios produce the backlog. Because it drives the real protocol path, the resulting state is genuinely cryptographic rather than forged, which is precisely what a hand-written row-inserting seed script can never achieve for MLS. Routing it through the scaffolded pytest deletes the usual seed-script-versus-test-suite split before it starts, and trace-events means the verification oracle costs nothing to build.
Downsides
A scenario format is a small language, and small languages grow: keep it declarative and resist making it Turing-complete. Scenarios encode assumptions about message and vote encoding, so they need an owner and will break when those change — the golden-file diff is what makes that break loud instead of silent. Wall-clock timelines need to be simulated rather than actually waited out.

Bunker-minted personas — copy no secret at all

Description: Mint dev personas with pacto-bot-admin new --backend bunker_local instead of --backend nsec, so the identity lives behind a local NIP-46 signer and no private key is ever written into a config file, an env var, or a shell script. The dev stack already runs a nip46-bunker container; today seed-squad.sh only ever uses the nsec backend and then extracts raw keys to pass around.

Axis
identity-bootstrap
Basis
direct: --backend accepts nsec (documented "dev-only"), bunker_local, and bunker_remote (admin.rs:274-277), with test-bunker <BOT_ID> (admin.rs:379-384) to verify a connection and pubkey match. The dev stack's compose file already runs a nip46-bunker service. --emit-secrets exists precisely because printing raw keys is otherwise deliberately avoided (admin.rs:369-371).
Rationale
Every other idea here — the persona cast, zero-click login, the handoff bundle — assumes a key gets copied from somewhere into the app's keystore, and then spends effort making that copy safe. This removes the copy. It is the difference between a faster way to move a secret and not needing to move one, and it retires the standing caveat that committed fixture identities leak their own nsec and EVM key to anyone with file access.
Downsides
Adds a live dependency: the bunker must be running for a persona to sign anything, so a developer offline or with a half-started stack gets a confusing failure rather than a clean one. It also exercises a NIP-46 path the desktop app may not fully support today — worth confirming before committing, since a persona that cannot sign is worse than one with an exposed throwaway key. Best treated as the eventual default rather than the first move.

11

Safe persona handoff — only if you must transfer

Description: If a developer genuinely needs to become a persona rather than join alongside it, the transfer must be one composed operation, never a sequence of individually-safe primitives a hurried developer can mis-order. A single handoff entry point that: retires the source atomically at export (revoking SendGroupMessages, ReceiveGroupMessages, CreateMlsGroup, InviteToMlsGroup in the same transaction that writes the bundle), re-keys on import (open the store with the bundle's raw key, copy group state, rewrite under a freshly PIN-derived key, then shred the imported key), and marks the bundle consumed so a second import fails loudly instead of forking the ratchet.

Axis
identity-bootstrap
Basis
direct: export is read-only today and mutates nothing about the source (admin.rs:1752-1826), while stamping split_brain_warning: true on every payload (admin.rs:1606) — a hazard the tool announces but leaves entirely to operator discipline. Import is idempotent with no memory of prior imports (admin.rs:1868-1970). The re-key requirement is forced by a verified asymmetry: bot-api mints a raw random 32-byte key via getrandom into a .key sidecar (mls_key.rs:129-137), whereas pacto-app derives its key from PIN and salt — both feeding the identical EncryptionConfig::new(key) (admin.rs:1850, mls.rs:324-325).
Rationale
Ranked last on purpose: this is the idea you only build if #8 turns out to be insufficient. But if transfer does happen, these are not optional refinements — they are what makes it shippable. Without re-keying, import either bolts a raw-key unlock path onto the app (a permanent bypass of PIN gating) or the store simply will not open under normal unlock. Without atomic retirement, a hazard the tooling already warns about is left to memory. A hazard that a tool announces and does not prevent is one that eventually fires.
Downsides
Substantially more work than #8 for a narrower case, and it spans two repos' security models, so it needs an owner on both sides. Re-keying means walking MDK's storage trait rather than copying a file, which couples the implementation to mdk internals and to the version parity that makes this possible at all — parity that is true today and nobody currently enforces.
