Ideation

@ Mentions in Squad Channels

Repo-grounded ideation for adding @ mentions to Pacto squad channels. Seven ranked directions survive from 41 raw ideas across five topic axes.

Date: 2026-07-20 Topic: at-mentions-in-squad-channels Mode: repo-grounded Focus: "I want to be able to mention someone with '@' in a squad channel."

Grounding Context

Pacto is a Tauri v2 desktop app: SvelteKit/Svelte 5 SPA frontend in src/ and Rust backend in src-tauri/src/. Squad channels are MLS groups over Nostr (Kind 444), with per-account SQLite storage.

  • Shared composer: src/components/dm/MessageInput.svelte is a plain textarea used by both DMs and squad channels.
  • Roster data already loaded: membersByGroupId and the $profiles store provide nickname, name, display_name, and avatar keyed by npub.
  • Rendering pipeline: src/lib/utils/message-formatting.ts runs Markdown → Linkify → DOMPurify sanitize → Twemoji → DOMPurify sanitize.
  • Notification gap: MLS messages update the UI but do not currently drive per-channel unread or highlight state for @mentions.
  • Privacy posture: Group content is encrypted inside MLS; relays see only the group h tag and ciphertext.

Topic Axes

  1. 1 Composition trigger — How the user types @ and selects a member.
  2. 2 Identity resolution — Which identifier to use and how to keep it stable.
  3. 3 Wire format / rendering — How mentions are serialized and rendered safely.
  4. 4 Notification / highlight — How the recipient gets notified.
  5. 5 Privacy and metadata — Whether mentioning leaks information outside the MLS group.

1

The default @mention stack

Cross-cutting Medium complexity Confidence 85%
Description
Type @ to trigger an inline autocomplete fed by the current squad roster and $profiles. When a member is selected, insert a stable canonical token (e.g., [@npub1...] or @npub1...) at the cursor. On the receiving side, the message passes through the existing formatMessageContent pipeline; a preprocessor converts the token into a safe <span class="mention" data-npub="..."> before markdown and sanitization run. After MLS decryption, the frontend scans the message for the current user's npub and, if found, triggers a highlight and a squad-hub alert. This is the smallest coherent path that satisfies the user's request without adding a new backend parser, protocol envelope, or metadata surface.
Basis
direct: MessageInput.svelte is the shared textarea composer; membersByGroupId and $profiles already provide completion data; formatMessageContent runs Markdown → Linkify → Sanitize → Twemoji; and the mls_message_new event is already emitted to the frontend.
Rationale
It reuses the existing roster, rendering pipeline, and event bridge. Every piece has a known home in the codebase, so the feature can ship as a frontend-only change rather than a protocol redesign.
Downsides
Inline autocomplete over a raw textarea requires caret-position tracking or a hidden mirror layer. Display names must be resolved locally, so a member with a stale profile cache may see raw npubs until profiles load.
2

Go-to-Member Fuzzy Palette

Composition trigger Medium complexity Confidence 75%
Description
Instead of an inline dropdown floating over the textarea, typing @ opens a fuzzy command palette modeled on an IDE's "Go to Symbol." The palette filters on nickname, name, display_name, and npub, and inserts a stable npub token at the cursor when the user selects a match. This avoids the fragile coordinate math of positioning a pop-up over a raw textarea.
Basis
direct: MessageInput.svelte uses a standard <textarea rows="1"> and handleKeydown is the central interception point for character-level triggers.
Rationale
Squad rosters can be noisy and profile names change. A fuzzy palette reduces friction and mis-mentions while sidestepping the most common implementation risk of textarea autocomplete overlays.
Downsides
A modal breaks the flow of a continuous chat composer; it may feel heavy for small squads. It also requires a new keyboard shortcut or a clear dismissal behavior.
3

Mention by npub, render by nickname priority chain

Identity resolution Low complexity Confidence 90%
Description
Store the raw npub as the canonical mention identifier on the wire, but render the mention using the same priority chain the rest of the app already uses: nickname → name → display_name → shortened npub. When a profile updates, the rendered mention automatically reflects the new name without invalidating the message or requiring a message edit.
Basis
direct: src/lib/utils/profile.ts resolves names in this priority: nickname, Nostr name, display_name, shortened npub, 'Unknown'.
Rationale
Display names in a group change frequently. Binding the mention to the unforgeable npub keeps the reference stable while the UX still feels like @displayName. It avoids inventing a parallel mention-name resolution system.
Downsides
During network lag or before profiles load, the user may see a raw npub. Two members with the same display name still require disambiguation at compose time.
4

Inline mention tag pre-processed before the markdown pipeline

Wire format / rendering Medium complexity Confidence 80%
Description
Before marked runs, replace resolved @handle tokens with a safe <span class="mention" data-npub="...">display name</span>. Then add span and data-npub to the DOMPurify allowlist, mirroring how the existing sanitizeWithEmoji hook validates Twemoji src attributes. The rest of the pipeline remains unchanged.
Basis
direct: formatMessageContent runs parseMarkdown → linkify → sanitize → replaceEmoji → sanitizeWithEmoji; the sanitizeWithEmoji hook pattern already validates structured attributes.
Rationale
It avoids forking the rendering pipeline into a separate DOM pass. XSS guarantees stay centralized in the existing strict allowlist, and the code pattern is already proven for spoilers and emojis.
Downsides
The allowlist must be widened carefully. A bug in the preprocessor could allow arbitrary span or data-npub attributes through the sanitizer.
5

Personal mention alert in squad-hub-alerts

Notification / highlight Low complexity Confidence 85%
Description
Extend the existing personalAlertsNeededBySquadId boolean store so a squad channel can show a badge when the current user has been explicitly @mentioned. The badge is distinct from the existing join-request and roster-signer alerts, so the user knows the alert is personal attention, not a governance action.
Basis
direct: mls_message_new currently updates the message list but does not increment a per-channel unread count, while personalAlertsNeededBySquadId already drives Channel.svelte badges.
Rationale
It compounds the existing alert store rather than duplicating the DM unread system. This gives squads a lightweight "you were mentioned" signal without the scope of full per-message read receipts.
Downsides
A boolean alert cannot distinguish one mention from ten in the same channel. It may need a companion "mentions list" view to be truly useful.
6

Quiet-by-default notifications with @-only bypass

Notification / highlight Medium complexity Confidence 70%
Description
Invert the default notification model for squad channels: they are muted for all members except when a message contains @your-npub. This removes the notification fatigue of every MLS message and makes the mention action meaningful again. The policy is enforced client-side by scanning decrypted messages for the user's own npub.
Basis
direct: DMs have a robust last_read and unread count system, while squad channels rely on a simplified alert model; the app already uses tauri-plugin-notification for native alerts.
Rationale
Squad channels can be high-volume. Without this, every message feels like a mention and @mentions lose their signal. It also aligns with the user's stated need to "get someone's attention."
Downsides
Users may miss important non-mentioned messages unless they actively check the channel. Per-channel or per-user overrides may be needed.
7

Plaintext-first private mentions

Privacy and metadata Low complexity Confidence 90%
Description
Mentions are ordinary text tokens inside the encrypted message content. The relay and backend never parse them; each client scans decrypted messages for its own npub and highlights accordingly. No separate mention envelope, no structured metadata, and no new Nostr event kind is introduced.
Basis
direct: DmMessage stores only a content string; MlsGroupMessage (Kind 444) encrypts content to the group and only members can unwrap it.
Rationale
It preserves the privacy-first architecture. Adding mentions leaks no additional metadata to relays, backend operators, or non-members, because the mention is just structured text inside an already E2EE message.
Downsides
The backend cannot compute aggregate mention statistics or send push notifications on behalf of offline users. Client-side scanning must be efficient in large channels.
