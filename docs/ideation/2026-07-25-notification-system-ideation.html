Ideation

A Calm Notification System for Pacto

Simple, doesn't annoy people, alerts people to missed items, and lets them review missed notifications easily — without a huge influx. Grounded in issue #148 (notification preferences: sounds, per-chat mute, mute-all).

Grounding Context

Codebase context. Pacto is a Tauri v2 desktop app (SvelteKit frontend, Rust backend, Nostr NIP-17 DMs + MLS group messaging, EVM governance). The striking finding: most of the notification backend already exists but is unreachable.

  • Unwired backend. audio.rs implements NotificationSettings{global_mute, sound} with 4 registered commands (get/set_notification_settings, preview_notification_sound, select_custom_notification_sound) — zero frontend callers. profile::toggle_muted is registered — zero frontend invocations or listeners (while toggle_blocked is fully wired and serves as a template). chats.muted is persisted and honored by notify gating and the unread counter — but no setter command exists, so it is always false.
  • Alert delivery. OS notifications flow through one choke point, show_notification_generic (lib.rs:3631): gated only on window focus, fired per message, no batching, no rate limit, no severity. The MLS group gate !chat.muted && !message.mine is copy-pasted at three call sites. The frontend Web Notification path never requests Notification.permission and silently no-ops. In-app toasts are single-slot, auto-dismiss, zero history.
  • Unread & badges. The frontend unread store hydrates npub1-only (all MLS/squad chats dropped); MLS last_read stays empty forever yet feeds the OS badge; the OS badge is not recounted on MLS arrival; frontend badges ignore mute while the backend counter skips muted chats — the surfaces disagree.
  • Missed-items review. Nothing exists. The __pacto_app__ inbox thread ingests only squad-invite DMs; MLS welcomes are consumed silently; announce/governance cards live only in scrollback; join requests are badge-only with a 24h localStorage cooldown. Governance events are all passive: dashboard polls have no deadline field at all, and no reminder path exists anywhere.
  • Settings shell. Section list hardcoded in SettingsPage.svelte:9-15 + settings-section-collapse.ts (5 sections, none for notifications); collapsible-section and optimistic-checkbox patterns are ready to reuse.

Past learnings. None — docs/solutions/ does not exist in this repo. This work is a candidate for the first captured learning after it lands.

External context (research value: high):

  • Slack's 2026 notification rebuild — decouple what you get notified about from how you get interrupted; three per-channel options (All / Mentions / Mute); "off" must never silently keep badging; 5x settings engagement post-launch.
  • Slack Activity tab — "A feed flows past you. An inbox waits for you, lets you process it on your terms, and feels done when you're done." One triage surface with filters, bulk-clear, mark-all-read.
  • Notification UX design guidelines — severity tiering (only high-attention earns interruption), snooze-with-expiry over permanent mute, Meta's "less is more" study (volume cuts recovered with net satisfaction gains), Element/Matrix quiet-by-default room modes.
  • Windows notification UX guidance — notification center as durable, dismissible storage for silent notifications.
  • Notification blindness — iOS Scheduled Notification Summary: bundle the non-urgent, let time-critical through.

Market signal. Notification overload is a top-3 support-ticket driver at Slack; mute-as-default is the norm in high-frequency products. Quiet-by-default is table stakes — the opportunity gap is the review experience. Governance (proposals, vote deadlines) gives Pacto genuinely time-sensitive items most messengers lack: a severity tier no chat app can copy.

Topic Axes

  1. Alert delivery — sounds + OS toasts: when to interrupt, batching, severity
  2. Mute & preference controls — per-chat/global mute, sound prefs, settings UI
  3. Unread & badge surfaces — chat-list badges, tab dots, OS counter
  4. Missed-items review — inbox/center/digest (greenfield)
  5. Governance & time-sensitive events — proposals, votes, deadlines, join requests

Ranked Ideas

Jump to
  1. Wire the mute + sound backend end-to-end (issue #148)
  2. One typed notification pipeline: durable log + severity router
  3. The Inbox becomes the missed-items surface
  4. Three-tier severity taxonomy, decided once
  5. Burst collapse: one self-updating notification per chat
  6. One watermark truth for every badge
  7. closes_at + an escalation ladder for governance deadlines
The combination worth noticing

Ideas 1–5 assemble into one coherent v1 — the calm stack: the #148 wiring (idea 1) is the entry point; the severity table (idea 4) is the policy; burst collapse (idea 5) and quiet defaults keep volume low; the pipeline (idea 2) routes everything; the review surface (idea 3) guarantees nothing silent is ever lost. Each stands alone, but they were generated to interlock.

1. Wire the mute + sound backend end-to-end (issue #148)

Mute & preference controls Confidence 90% Complexity: Medium
Description Pacto has a fully implemented notification-preference backend that no user can touch: all four audio commands are registered with zero frontend callers, toggle_muted emits profile_muted to no listener, and chats.muted is honored everywhere yet has no setter — it is always false. Add the Notifications settings section (sound picker + preview + custom upload + global mute), a per-chat mute toggle in thread/channel options backed by one new chat-mute setter command, and profile mute wired by copying the toggle_blocked template verbatim (API wrapper, dropdown item, store listener). This is issue #148's acceptance criteria, framed as pain relief: the silence controls exist in the DB but are unreachable.
Basis direct: grep over src/ for toggle_muted, profile_muted, and the four audio commands returns no callers (verifier-confirmed); "No command can ever set chat.muted; it is always false" (evidence dossier, confirmed); settings sections hardcoded at SettingsPage.svelte:9-15; toggle_blocked wired end-to-end as the template (nostr.ts:221-223, DmThread.svelte).
Rationale Today a user spammed by a busy MLS group has literally no recourse — not per-chat, not per-profile, not global — because every mute path dead-ends in an unwired command. This closes issue #148 entirely with effort M and low risk, and it is the enforcement half of every other idea here: severity tiers and quiet defaults are meaningless if users can't reach the controls.
Downsides Pure wiring, no new capability — it makes the current (per-message, focus-gated) alert behavior mutable, not better. Muted-chat badge semantics (backend zeroes muted counts, frontend doesn't) must be decided as part of this work or the disagreement ships to users. Stringly SQL preference keys (notif_global_mute, notif_sound) get calcified a little more with each consumer unless a versioned prefs record is chosen at the same time.

2. One typed notification pipeline: durable log + severity router

Alert delivery Confidence 80% Complexity: High
Description Today OS alerts, sounds, toasts, badges, and announce cards each travel their own ad-hoc path; the only shared point is show_notification_generic (focus-only gate, per-message, no batching or severity), and the MLS mute gate is copy-pasted at three call sites. Introduce a single NotificationEvent envelope (kind, actor, target chat, payload ref, timestamp) emitted by every producer — DM handlers, MLS text/file/poll handlers, welcomes, announce ingestion — into one Rust pipeline that applies visibility/mute/severity policy once, writes every accepted event to a durable per-account log, then fans out to OS toast, sound, badge recount, and the review surface. The toast stops being the notification system and becomes a disposable pointer at durable state.
Basis direct: show_notification_generic (lib.rs:3631) gates only on is_focused(); the gate !chat.muted && !message.mine repeats verbatim at lib.rs:2171-2176, 2259-2264, 2388-2392; NotificationData.notification_type exists but no policy consumes it; showToast begins with clearToast() and auto-dismiss records nothing (toast.ts:62-81). All verifier-confirmed.
Rationale A choke point is the highest-leverage artifact a notification system can own: severity, batching, rate-limiting, and mute policy are written once and inherited by every current and future event type — deadline reminders and digest entries become new producers, never new gating debates. The three duplicated MLS gates are already proof of the drift this prevents. It also fixes the raw-announce-JSON leak and toast-clobbering data loss as side effects.
Downsides The biggest change in the set: touches every producer call site and needs the durable log schema up front. Sequencing risk — done before ideas 3–5 it is a large refactor with no user-visible payoff until they land; done after them it means migrating their call sites a second time. The visibility signal (active thread + scroll pin) lives in the frontend today, so the router either consumes a frontend hint or duplicates that state.

3. The Inbox becomes the missed-items surface

Missed-items review Confidence 85% Complexity: Medium
Description The app already has the skeleton of a notification center — the pinned __pacto_app__ Inbox thread with per-npub persistence, an unread watermark, and an undeletable row — but it ingests only squad-invite DMs, while everything else lands nowhere reviewable. Widen the routing predicate to typed catch-up items: MLS welcomes, join-request outcomes, governance inbox-bucket events, mentions, and a bounded toast log — each with a deep link, cleared individually or swept with mark-all-read. The inbox row's badge becomes the single "you have unread stuff" signal; interruption stays reserved for what earns it.
Basis direct: the routing predicate is literally invite-only (pacto-app-inbox.ts:26-29, verifier-confirmed); dossier gap summary: welcomes have no UI consumer, join outcomes are one-shot DM divs, toasts are never logged, hub alerts are counts with no enumerable events, governance inbox-bucket items have no reader. external: Slack Activity — "An inbox waits for you, lets you process it on your terms, and feels done when you're done"; the missed-items surface is a distinct pattern from per-chat badges, not a replacement.
Rationale This is the direct answer to the user's ask — "review missed notifications easily without a huge influx" — and the market gap: quiet-by-default is table stakes, the review experience is the differentiator. Reusing a pinned, persisted, watermark-cleared thread keeps it small: routing predicates, item renderers, and mark-all-read, not a new subsystem. It also makes every other quiet idea safe — silent items are never lost, they accumulate in exactly one place.
Downsides Scope creep is the failure mode: which event types earn an inbox item in v1 (welcomes and join outcomes are unambiguous; toast history and mention rollups are taste calls) needs an explicit cutoff or the list becomes a second firehose. A chat-thread-shaped surface constrains richer per-item actions (snooze, dismiss) later. Two ordering models are viable — extend-the-inbox vs a dedicated surface — and the choice should be made deliberately in a brainstorm, not drifted into.

Today — lands nowhere

  • MLS welcomes → store, no UI consumer
  • Join-request outcomes → one-shot DM divs
  • Toasts → single slot, clobbered, never logged
  • Gov inbox-bucket events → no reader
  • Hub alerts → counts only, events not enumerable

After — one reviewable list

  • Typed items with actor / what / when
  • Deep links into the source surface
  • Cleared individually or mark-all-read
  • Silent by design — zero new interruptions
  • "Feels done when you're done"

4. Three-tier severity taxonomy, decided once

Alert delivery Confidence 80% Complexity: Low
Description Decide once, in one table, which event kinds are Interrupt (OS toast + sound), Record (silent; lands in the review surface + badge), and Passive (inline card only, no count). The interrupt criterion is actionability — does this demand an action from this user now? Human DMs, mentions, invites, and time-sensitive governance earn Interrupt; group chatter defaults to Record; deploy/sync announces stay Passive. Adding a new event type means assigning it a tier, not re-litigating "should this interrupt?".
Basis external: ICU alarm-fatigue redesigns — the structurally exact analogy (same constraints: interruption cost measured in missed critical events; same failure mode: per-event alerting trains users to ignore everything) — converged on "an alarm sounds only when it demands action from this person now"; Slack's rebuild decoupled what-notifies from how-it-interrupts (5x settings engagement). direct: today the only tier is implicit — every non-muted group message fires the gate at lib.rs:2171-2176; NotificationData has no severity field consumed on desktop.
Rationale Severity is the compounding decision: one table turns "simple, doesn't annoy people" from taste into enforceable code, and it makes quiet defaults safe — Record-tier items are never lost, just not interrupting. Users mute whole chats to escape noise and then lose the one actionable item inside them; actionability (not source) as the criterion is what lets a busy squad stay unmuted safely.
Downsides The tier assignments are product-taste calls (are squad invites Interrupt? are new polls Record or Passive?) that must be debated once in a room — the idea's deliverable is that debate happening, which some teams will experience as process. A static table can't express per-user or per-chat overrides without the preference layer from idea 1 landing first.

InterruptOS toast + soundDM from unmuted peer · mention · squad invite · governance deadline escalation
RecordSilent → review surface + badgeGroup chatter · join-request outcomes · welcomes · new polls

5. Burst collapse: one self-updating notification per chat

Alert delivery Confidence 85% Complexity: Low
Description Every accepted message currently calls show_notification_generic individually — one active MLS group produces a per-message OS toast storm. Key the choke point by chat_id with a short quiet window: the first notifying message fires normally; subsequent arrivals update that same notification into a count ("Alice · #governance — 6 new messages") instead of stacking six banners. Mention-class items inhibit the generic burst for that chat. Persist the welcome-dedup set (NOTIFIED_WELCOMES is a volatile in-memory HashSet that re-fires after every restart) while in the area.
Basis direct: "No rate limiting, no batching, no collapsing: every accepted new message calls show_notification_generic individually" (dossier; call pattern confirmed at lib.rs:2190, 2278, 2401); welcome dedup is an in-memory lazy_static HashSet (lib.rs:189-191). external: Prometheus Alertmanager's grouping + inhibition is the infrastructure industry's proven answer to the identical storm problem; iOS Scheduled Notification Summary validates bundling at consumer scale.
Rationale Burst storms are where "annoying" is born — a single excited sender can produce a dozen banners in a minute, and notification overload is a top-3 support-ticket driver at Slack. Collapse deletes interruptions wholesale rather than tuning each one, works even for chats the user deliberately keeps unmuted, and scales from 1 message/day to 1000 with zero user configuration.
Downsides Per-platform update/replace semantics in tauri-plugin-notification need a spike — if replacement isn't supported on a platform, collapse degrades to coalesced-delay (hold 10s, send one summary). Slightly stale previews are the price of calm. Choosing the group key (chat? sender×chat?) and window length are real taste calls.

6. One watermark truth for every badge

Unread & badge surfaces Confidence 85% Complexity: Medium
Description Pacto runs two divergent unread implementations that actively disagree: the frontend blind-increments DM badges with no mute check while the backend counter skips muted chats; the frontend hydrate drops every non-npub1 chat (all MLS/squad conversations); MLS last_read stays empty forever yet feeds the OS badge; and the OS badge is never recounted on MLS arrival. Fix it at the root: wire mark_as_read for MLS chats, recount on MLS arrival, hydrate all chats, and make the backend the single owner — computing mute-aware per-chat counts on every state change and pushing them to sidebar rows, tab dots, and the OS badge. The badge contract becomes: badge ⇒ an unseen item exists in a reviewable surface; muted ⇒ no badge anywhere.
Basis direct: if (!c.id.startsWith('npub1')) continue; (dm-unread.ts:69) drops MLS chats from hydrate; incrementDmUnread is a blind +1; update_unread_counter is called only from DM handlers and mute/block toggles — never on MLS arrival; mark_as_read has exactly one frontend call site; the frontend/backend mute disagreement is confirmed in code. All verifier-confirmed.
Rationale A badge that disagrees with itself trains users to ignore badges entirely — silently defeating every other missed-items idea in this set. One watermark is the compounding primitive: fix it once and chat-list badges, tab dots, the OS counter, and the review surface's "new since" line are all consistent by construction, and an entire bug class (cross-surface reconciliation) is deleted rather than patched forever.
Downsides Recount cost per arrival on large chat sets is a real performance question (mitigable: increment-then-periodic-recount). Muted-chat badge policy (zero everywhere vs dimmed sidebar badge) is a user-visible semantics decision that must be made explicitly. Sequencing with the frontend's window-limited recount logic needs care during cutover.

7. closes_at + an escalation ladder for governance deadlines

Governance & time-sensitive events Confidence 65% Complexity: Medium
Description Governance is the one place Pacto has genuinely time-sensitive items, yet nothing about them is time-aware: DashboardPollDto has no deadline field at all, polls list forever oldest-first, on-chain proposal deadlines render as passive text, and no reminder path exists anywhere. Add a single optional closes_at_ms to the poll DTO and wire format (greenfield — breaking change acceptable), then attach a proximity ladder earned by time-remaining, not volume: silent review-surface entry at T-7d, badge at T-48h, exactly one OS alert in the final hours if the user still hasn't acted. On-chain proposals get the same ladder from their existing deadline field.
Basis direct: DashboardPollDto fields are id/parent_id/title/description/options/created_at_ms/created_by_npub — no expiry (verifier-confirmed dashboard_poll.rs:236-244); polls list ORDER BY created_at_ms ASC with no close filter; grep finds no reminder logic anywhere; deadline renders as passive meta text. external: ATC trajectory alerting (MSAW) — alarm because the future intersects a floor, timed to when action still matters; iOS summaries let time-critical alerts through the batch.
Rationale Missed votes and expired proposals are the costliest missed items in a governance app — far worse than a missed chat message — and today they are the least alerted. One perfectly-timed escalation per deadline is the highest signal-to-interruption ratio the system can offer, and it justifies the entire severity tier: the one interrupt no user will call annoying, and the one no competing messenger can copy.
Downsides Cross-layer commitment: a wire-protocol field (MLS Kind 30078), a scheduler, and per-squad policy (default lead times, who qualifies as "hasn't acted"). Polls without closes_at never remind — an honest limitation users must understand. Getting the ladder wrong (too early, too repeat-happy) re-creates the annoyance problem inside the highest-stakes surface, so the escalation contract needs the same one-time debate as the severity table.
