Ideation artifact

NFTs for identity, money and fun in Pacto

Date: 2026-07-25
Topic: nft-identity-monetization
Mode: repo-grounded
Source: issue #124 — NFT name claims w/ embedded images

Focus: how Pacto can use NFTs for identity, money-making, and other fun blockchain features — creative but practical, and simple enough that a non-crypto member can use it. Issue #124 proposes four things at once: an on-chain-rendered identity image, an NFT contract as the Pacto name-claim database, a mint fee as a “Nitro” income source and spam deterrent, and NFT token-gating for events and spaces. This set treats those four as separable decisions rather than one feature.

Grounding Context

Codebase context

Identity. The npub is the identity root; the same BIP-39 seed derives the Nostr keypair and the EVM wallet. Display names resolve nickname → name → display_name → short npub. The nip05 field is copied verbatim out of Kind-0 metadata and rendered with a green checkmark — a repo-wide search finds no .well-known/nostr.json fetch anywhere, so the checkmark verifies nothing. Mention collisions fall back to a shortened npub. There is no name registry, no uniqueness constraint, and no alias reservation in the codebase.

Roster binding. V16__squad_member_evm.sql stores (parent_id, member_npub) → evm_address as a composite primary key; access_control/identity.rs returns ACL_UNBOUND when no roster EVM is linked. This is the strongest existing npub↔address anchor, and it is already fail-closed.

Gating. GovCapability is a 14-variant enum evaluated by require_capability() against Hats Protocol wearer checks. Verification counted 6 call sites, each hardcoding a fixed variant, and capability_allowed()’s match arms are grouped by shared logic. Squad membership is a three-signal OR-gate: if in_mls || has_evm_binding || has_roster_address. Channels carry access?: 'open' | 'closed'. Everything fails closed.

Money. Native and ERC-20 sends work (ETH, USDC, USDT). A per-squad sponsor pool funds gas; governance writes route via EOA when the roster key can pay, or via sponsored ERC-4337 UserOps when it cannot. deposit_squad_sponsor is member-callable, not admin-only. Safe factory bindings exist but no payout logic. There is no fee extraction, no premium tier, no “Nitro”, no subscription, and no tip or zap anywhere in the repo.

Visuals. getProfileAvatarSrc in src/lib/utils/profile.ts is the sole avatar entry point — verification confirmed all 13 importers character-for-character. Today it falls through to a first letter over a hashed HSL gradient. No SVG generation, no data-URI construction, no badge component exists. The attachment pipeline (AES-256-GCM, Blossom, SHA-256 dedupe, per-account image cache) is mature.

Chain UX. Account creation needs zero crypto knowledge. The first on-chain action does not: it requires picking a network, holding native gas, and understanding the signer split. Squad infra locks to one network at first deploy. SQUAD_DEPLOYABLE_CHAIN_IDS is currently ['sepolia', 'local'] — there is no mainnet or L2-mainnet deployment yet.

Prior ideation — the live tension

docs/ideation/2026-07-20-npub-identity-ideation.html ideated on npub identity three weeks ago and explicitly rejected global username uniqueness as “a losing battle in a permissionless network,” settling on roster-scoped identity, petnames, and verified NIP-05. Issue #124 proposes exactly the global name registry that run rejected. The mechanisms differ — that run only weighed free off-chain naming, while #124 proposes a scarce, paid, on-chain one — so the question is genuinely reopened rather than already settled. Several ideas below exploit that tension directly.

External context (2026)

  • On-chain rendering — tokenURI() returning a base64 data-URI SVG is standard (Nouns, Autoglyphs, Blitmap). Feasibility is not the trap; gas is. The viable shape is an L2 plus composable primitive layers from small on-chain tables, not raster-equivalent detail.
  • Name registries — ENS v2 2026: $8/yr for 5+ chars, $160/yr for 4, $640/yr for 3, at ~2.8M names across ~640K owners. Verification correction: ENS has charged recurring annual fees since inception, and its own 2026-04 proposal presents the “82% registered longer than intended” figure as evidence the multi-year discount worked. Basenames (Base L2, near-zero cost) is the closest comp. Farcaster fnames are free, off-chain, and policy-gated — proof a fee is not required when something else enforces usage.
  • Token-gating UX — the universal break point is wallet-connect plus signature. The 2026 fix is embedded wallet plus ERC-4337 sponsored transactions. Pacto already ships both.
  • Monetization comparators — Discord Nitro Basic $2.99/mo, full $9.99/mo ($99.99/yr); what people buy is cosmetics and status, not utility, and Server Boost is a pooled community tier (~$42-100/mo across members). Nostr’s own working monetization is NIP-57 zaps — small, per-post, value-for-value. Paid NIP-05 providers sell a signed handle, not a token.
  • Failure post-mortems — POAP entered maintenance mode 2026-03-16 after 7.2M badges. Verification correction: POAP’s stated cause was limited growth and classification friction from its 2023 commercial-pricing pivot; “transferability destroyed credential value” is a third-party analysis, not POAP’s own account. Friend.tech’s collapse (TVL $52M → ~zero) is unambiguous: speculation with no retained utility, a bonding-curve spread causing instant paper loss, a 5% platform fee. Tradeable social-access keys are a known collapse pattern.
  • Sybil reality — an NFT’s “unique wallet count” proves unique addresses that minted, trivially gamed on sponsored-gas L2s. The honest framing is “claims”, never “humans”.

Institutional learnings

docs/wallet/PROTOCOL_ADDRESS_BOOK.md (compile-time JSON address book, operator env override), docs/wallet/PACTO_SQUAD_SPONSOR.md (the existing route for paying someone else’s gas), docs/governance/ACCESS_CONTROL.md (fail-closed capability matrix, two coexisting trust paths), docs/wallet/CHAIN_CONFIG.md (per-squad chain lock — a fragmentation-avoidance precedent any registry must reckon with).

Topic Axes

  • A. Name claim & uniqueness — what a Pacto name is scoped to, how it is claimed, renewed, disputed or lost; squatting and collisions; what “unique users” can honestly mean.
  • B. Visual identity & collectibles — the on-chain-rendered image, how it reaches the render surfaces, badges, attendance proofs, cosmetics.
  • C. Mint economics & revenue — pricing shape, fee routing, who receives the money, what “Nitro” actually sells, recurring vs one-time.
  • D. Token-gated access & perks — gating events, spaces, channels, features or governance weight; how it plugs into the existing capability and membership checks.
  • E. Chain-invisible UX & onboarding — making the mint and the gate feel like a normal app action; sponsored gas, chain choice, error vocabulary, what the user never has to see.

1.

Invisible claim, visible everywhere

Axis E · Chain-invisible UX Confidence 85% Complexity Medium
Description

Delete “mint” as a user-facing verb entirely. During account setup the user types a name into one field — the same gesture as setting a nickname today. Behind that field, the claim mints through the existing sponsored ERC-4337 path, so no price, no balance, no network picker and no wallet screen ever appears. The resulting on-chain SVG is then resolved by getProfileAvatarSrc, which is the single avatar entry point in the codebase, so the new identity image lands on all thirteen render surfaces at once without touching any of them. The whole feature reduces, from the member’s side, to “type your name, get a face.”

Basis

direct: getProfileAvatarSrc is defined once in src/lib/utils/profile.ts and imported at thirteen call sites — ChatView.svelte, CommonsBroadcastCard.svelte, CommonsBroadcastDetailModal.svelte, CommonsPersonalPanel.svelte, DmThread.svelte, MessengerNavbar.svelte, DeploySafeModal.svelte, DashboardCrewTab.svelte, ParentDashboardMembersPanel.svelte, ProfileSection.svelte, WalletBar.svelte, resolve-dm-message-presentation.ts and mention-autocomplete.ts. Independent verification confirmed this list character-for-character; it was the best-verified citation in the whole candidate set. Its current fallback is commonsTagGradient(seed) hashing into two HSL values plus a first letter.

direct: gov_module_write.rs already implements WritePath::Sponsored — roster key when it can afford the write, sponsored UserOp when it cannot. The mint reuses this rather than introducing a payment rail.

external: 2026 token-gating research names embedded wallet plus sponsored transaction as the documented best practice for hiding chain complexity. Pacto is unusual in already shipping both halves for a different feature.

Rationale

Issue #124’s mint fee is in direct tension with the “somewhat simple to use” bar, and the codebase already contains the resolution. The fan-out ratio is the real prize: one function edit converts a mint from “one more screen a user has to find” into “the thing they see everywhere their name already appears.” That changes how the feature should be priced and pitched — it is not a purchase, it is the default face.

Downsides

“The member never sees an error” is not literally true today. sponsor_userop.rs ships a live SPONSOR_POOL_LOW error (“sponsor pool below required headroom”), and BUNDLER_CONFIG and SPONSOR_PATH_UNAVAILABLE tell the reader to set BUNDLER_RPC_URL and PACTO_ERC4337_ACCOUNT_IMPL — language that assumes the reader already understands bundlers and 4337 accounts. Those strings need rewriting before this claim holds.

The funding cliff relocates rather than vanishes: whoever bootstraps a squad still funds the pool and picks a network. A silent mint also means the member never consciously agrees to an on-chain action, which is a consent question worth deciding deliberately. And if the mint is free and sponsored, the resulting mint count is trivially sybil-gamed — report it as “claims”, never as “unique humans”.

2.

The claim replaces the decorative checkmark

Axis A · Name claim & uniqueness Confidence 90% Complexity Medium
Description

Pacto currently renders a green checkmark next to whatever NIP-05 string a user put in their own Nostr metadata. Nothing verifies it. Rather than adding a second, better badge next to a broken one, delete the existing checkmark and make “holds an active on-chain name claim” the single verification signal shown anywhere in the product. This is a subtraction, and the NFT registry is the first mechanism in the codebase capable of making that signal true.

Basis

direct: src/components/settings/ProfileSection.svelte renders {#if profile.nip05}<p class="nip05">✓ {profile.nip05}</p>{/if}, and src-tauri/src/profile.rs only ever copies the claimed value out of Kind-0 metadata. Verification searched the repository for well-known and nostr.json and found zero hits — there is no verification call to be found anywhere.

direct: the roster binding (parent_id, member_npub) → evm_address in V16__squad_member_evm.sql gives the claim a checkable owner without inventing new plumbing.

Rationale

Users make real trust decisions — who to DM, who to treat as an officer — off a checkmark that means nothing. In an app whose whole proposition is trustworthy identity without KYC, a decorative verification badge is not a cosmetic bug; it is a social-engineering surface the product ships on purpose. This is also the cleanest answer to “what does the NFT actually buy us”: it buys the first verification claim Pacto can make honestly. Note that the prior ideation run reached the same target from a different direction — verified NIP-05 — so these are competing mechanisms for one slot, not complements.

Downsides

Removing the checkmark before the claim exists briefly makes the product look less trustworthy even though it becomes more honest. The claim is only meaningful where the reader can check it, so cross-squad and Commons surfaces need a resolution path or the badge silently degrades. And it competes head-on with the prior run’s verified-NIP-05 idea: NIP-05 costs a DNS lookup and no chain, this costs a chain read and no DNS. Picking both is worse than picking either.

3.

One balance check, many gates — plus time-boxed event passes

Axis D · Token-gated access Confidence 70% Complexity High
Description

Issue #124 wants NFTs to gate “special Pacto events, spaces, or features.” Pacto has exactly three places where that decision is made, and they are independent by design: require_capability() for the fourteen governance actions, Channel.access for spaces, and MLS welcome processing for group admission. Add one NFT-balance read that all three can consult, then mint event passes whose validity window lives in the token’s own metadata — so a pass is checked live at each door and simply stops mattering after the event, with no burn transaction and no revocation flow.

Basis

direct: the three seams are real and separately confirmed — require_capability<R: Runtime>(app, parent_id, capability, rpc_urls) fails closed via Err(wallet_err_json("ACL_DENIED", reason, None)); Channel.access?: 'open' | 'closed' in src/stores/squads.ts; and the invited_recipients resolution inside MLS welcome processing.

direct: the gating layer is genuinely agnostic to what answers the read. Verification confirmed require_capability / capability_allowed only ever consume a boolean populated by a swappable eth_call_decode — the same seam already used for isWearerOfHat. Whether the claim is an ERC-721, an ERC-5192 soulbound token or a pure attestation with no transferFrom at all does not change the gating code.

reasoned: an event pass whose expiry is baked into its own metadata never needs a revocation transaction, because validity is evaluated at presentation rather than stored as a grant. That removes the entire post-event lifecycle — the part where a permanent membership token becomes a stale credential nobody remembers to withdraw.

Rationale

This is the only idea in the set that turns issue #124’s vaguest line — “token gate special Pacto events, spaces, or features” — into something a team can actually scope, because it names the three functions that would change. It also cleanly separates “buy into one privilege” from “join the squad”: an event pass can open a channel without ever touching MLS, so it cannot be used to sneak into private messaging.

Downsides

The leverage is smaller than it first appears, and verification caught this. The tempting claim is “add one enum variant and gate any subset of the fourteen actions with zero new call sites.” That is wrong. There are six require_capability call sites, not four, and each one hardcodes its own fixed GovCapability; capability_allowed()’s match arms are grouped by shared logic, so ProposeTreasury and MutateTrackedTokens share an arm. Making gating configurable per squad needs new per-squad state plus restructured arms — a real project, not a one-line change. Complexity is High for that reason.

Three independent checkpoints also means three places to get consistency wrong: a pass that opens the channel but not the MLS group is a confusing half-admission. And per-squad gate configuration reintroduces exactly the class of captain error (a stale gate after a role change) that deriving gates from the existing capability ladder would have avoided — that alternative was considered and cut, but it is the honest counter-argument to this idea.

4.

Two-sided Nitro: cosmetics up, gas down

Axis C · Mint economics & revenue Confidence 65% Complexity Medium
Description

Stop treating “Nitro” as a subscription that unlocks features, and copy what Discord’s revenue actually is. Individuals buy small cosmetic layers for their own claim image — an alternate palette, an animated trait, a frame — with no functional value attached. Those payments land in the squad’s own sponsor pool via the member-callable deposit path, which is the same pool that pays everyone’s governance gas. When a squad’s aggregate cosmetic spend crosses a threshold, the whole squad unlocks a shared perk, mirroring Server Boost rather than Nitro-the-subscription. The loop is self-reinforcing: more cosmetics bought, more free gas for votes, more governance activity, more reason to be visible.

Basis

external: Discord Nitro Basic is $2.99/mo and full Nitro $9.99/mo ($99.99/yr) — figures confirmed in verification — and what people buy is cosmetics and status, not utility. Server Boost is a genuinely pooled community tier, with Level 3 reached at roughly $42-100/mo across multiple members. That is a structurally different product from “pay to unlock a feature”, which is what issue #124 currently implies by “Nitro feature income source”.

direct: squad_sponsor_deposit.rs exposes “send ETH to a squad sponsor clone via ISquadSponsorBase.deposit()”, and verification confirmed it is member-callable, gated by require_parent_member rather than captain-only. The pool exists today as a one-time, non-recoverable admin deposit; this makes it refillable by ordinary use.

external: Friend.tech is the boundary condition. Its collapse — TVL $52M to effectively zero, a bonding-curve spread causing an instant paper loss, a 5% platform fee — is what happens when social access becomes a tradeable market. Cosmetics with no functional value and no resale market cannot enter that failure mode.

Rationale

Issue #124 conflates two goals in one transaction: the fee should deter spam and generate income. Those want opposite pricing. Cosmetics separate them cleanly — spam deterrence moves elsewhere (see idea 6), and revenue attaches to something people demonstrably pay for repeatedly. It also makes the money legible to a no-KYC organizing tool’s members: they are topping up their own squad’s gas, not paying a platform rent.

Downsides

This does not fund Pacto, and that is the open fork. Verification’s sharpest finding was that no candidate mechanism in this run routes revenue to a Pacto-owned treasury — they all keep money squad-internal, redirect it to a member, or spend from the squad’s own funds. If “Nitro income source” means income for Pacto, this idea needs an explicit protocol cut on cosmetic sales, and that decision should be made deliberately rather than discovered later. A cut on cosmetics is the least objectionable place to put one, since nothing functional is being taxed.

Cosmetic demand is also unproven at Pacto’s scale — Discord’s cosmetics economy runs on hundreds of millions of users, and a private organizing tool with small squads may simply not have enough audience for status goods to matter. The pooled-threshold perk needs a visible progress bar or it feels arbitrary. And a cosmetics layer meaningfully increases the on-chain rendering surface, which is the part with real gas cost.

5.

Badges that are true by construction

Axis B · Visual identity & collectibles Confidence 80% Complexity Medium
Description

Add a post-success hook inside require_capability that mints a non-transferable badge tagged to the capability actually exercised — cast a mutiny vote, executed a treasury proposal, resigned as captain. Because the hook fires only after a real fail-closed check passes, the badge cannot be self-minted, bought, or claimed by someone who did not do the thing. Render the badges as a strip through the same on-chain SVG pipeline as the identity claim, and add one permanent trait for provenance facts that cannot become wrong later — “joined in the squad’s first 30 days” is the canonical case. This is the “fun” layer the user asked for, and it costs almost nothing once idea 3 exists.

Basis

direct: require_capability returns Ok(()) only after the check passes for one of the fourteen GovCapability variants. That is a single, already-fail-closed success path covering every governance action Pacto has — a badge minted there is a credential by construction rather than by policy.

direct: there is no badge component to collide with. The visual-identity scan found only a hasUnreadDot boolean in Tab.svelte — no trait display, no achievement scaffold, no indicator vocabulary. Greenfield.

external: ERC-5192 defines soulbound semantics precisely — locked() is true and transfers revert. Note the corrected history: POAP’s stated reason for entering maintenance mode in March 2026 was limited growth and classification friction from its commercial-pricing pivot, not transferability. The transferability critique is a third-party reading. It is still the right design call here, but on its own merits: a credential that can be bought stops being evidence of anything, and Pacto has no legacy transferable badges to migrate.

Rationale

Attendance badges are the obvious version of this and the weak one, because “showed up” is hard to prove and easy to fake. Capability-gated badges are strictly stronger: the chain already had to agree you were allowed to do the thing before you did it. That makes the collectible layer meaningful and cheap at the same time, and it gives Pacto a reason to render visuals for people who never bother customizing anything.

Downsides

Minting on every governance action multiplies transaction count and therefore sponsor-pool drain — this likely needs batching or a mint-on-first-occurrence rule rather than one token per vote. Badges tied to governance also only reward the governance-active minority; most members of most squads will have an empty strip, which is a worse look than no strip at all. And a badge that records “started a mutiny” is permanent political history inside a private organizing tool — some squads will consider that a feature and some a liability, so it should be opt-in per squad.

A related idea was cut for a reason worth carrying: deriving the identity image from governance state sounded compelling until verification found the field it relied on does not exist. HatContext has exactly roster_address, wears_captain, wears_crew and captain_is_safe — three usable booleans, no participation record. Most non-captains would render identically. Badges work where the derived-image idea does not, because a badge records an event rather than reading a state.

6.

Anti-squatting without a paywall

Axis A · Name claim & uniqueness Confidence 60% Complexity Medium
Description

Two mechanisms that together remove the fee from the anti-spam job entirely. First, never block a claim: the first mint of a string wins it outright, and a later mint of the same string is automatically differenced by the contract — “Atlas”, then “Atlas (2)” — with the suffix rendered into the SVG and treated as part of the name. Second, claims lapse unless used: a claim goes dormant after a period of inactivity unless renewed by a free, gasless signed Nostr event that the app can emit silently on launch, with the registry settling batches of renewal proofs periodically. Squatting becomes pointless because a hoarded name decays, and nobody is ever locked out of a name they wanted or charged rent to keep one they use.

Basis

direct: Pacto already has the collision failure and it is silent. src/lib/utils/message-formatting.test.ts contains a test literally titled “resolves multiple mentions with the same alias by occurrence order” — when two roster members display as “alice”, the resolver picks whichever mention appears first in an array, invisibly to the sender.

external: Farcaster fnames are free, off-chain, and policy-gated against squatting — direct evidence that a fee is not required when something else enforces usage. Membership registries have long used automatic differencing rather than refusal or auction; SAG-AFTRA requires a duplicate stage name to be distinguished before registration (the canonical case is Michael J. Fox). Two corrections from verification are worth stating plainly: SAG’s mechanism is a member-chosen distinguishing element rather than an auto-appended numeral, and the common claim that Harberger-style forced-sale pricing “never shipped” is false — Wildcards has run it on mainnet since around 2021. Neither correction breaks the mechanism proposed here, but neither analogy should be cited as precedent for it.

reasoned: a one-time fee is a single deterrent event, priced against a squatter’s expected resale value rather than against use. Decay prices against attention, which a squatter holding a thousand names cannot supply and a real user supplies for free by opening the app. That is why decay is a better fit than rent for a product whose bar is “somewhat simple to use”: the honest user never experiences a payment or a renewal decision at all.

Rationale

Issue #124 assumes the mint fee does double duty as revenue and spam control. The refuted candidate in this run was the one that argued ENS proves recurring rent is the anti-squatting lever — ENS has in fact charged annual fees since inception, so it demonstrates nothing about moving away from one-time fees. With that argument gone, the anti-squatting question is wide open and needs an answer that is not “charge money”. This is that answer, and it lets idea 4 own revenue cleanly without also having to be a deterrent.

Downsides

Auto-suffixing means the name a user typed is not always the name they get, which is a real disappointment at the exact moment of first use — the confirmation screen has to show the actual result before minting, not after. Decay is the riskier half: a lapsed claim means an identity silently disappears, which is far worse than a name being taken, so the dormancy window has to be long and the warning loud. Batched off-chain renewal proofs also introduce a settlement mechanism that has to be designed, indexed, and trusted — this is the least specified idea in the set, which is why its confidence is lowest.

Worth pairing with a reporting constraint that was considered separately and folded in here: whatever this registry counts, it counts claims. Sponsored minting makes sybil claims free, so a raw mint count can never honestly be described as “unique users” in the way issue #124 proposes. Counting only claims countersigned by an existing captain would give a defensible number, at the cost of a step most users would never take.

7.

Nostr-first claim, chain as the exception path

Axis E · Chain-invisible UX Confidence 75% Complexity Medium
Description

The deliberate counter-proposal. Decompose what issue #124’s NFT is actually doing and check whether each job needs a token. It is doing three: a name database, gating for events and spaces, and fee income. The name database is a signed replaceable Nostr event — same trust model as NIP-05, no wallet, no gas, no network picker. Gating already works through MLS membership and the three-signal check, with zero extra chain calls. That leaves income, and the chain artifact. Publish claims as Nostr events by default and escalate to an on-chain anchor only in three cases: a contested claim, a squad voting to federate its namespace, or a user who wants portable proof outside Pacto. Most claims never touch a chain at all.

Basis

external: Nostr’s own paid-identity market chose signatures over tokens. Paid NIP-05 providers sell a vanity DNS-backed handle for a few dollars; no squatting economy formed around them because NIP-05 is a pointer, not ownership. That is the clearest available counter-model to issue #124’s premise, and it comes from Pacto’s own protocol ecosystem rather than an adjacent one.

direct: the gating job is already done. squad_sponsor_common.rs implements the three-signal membership check — if in_mls || has_evm_binding || has_roster_address { Ok(()) } else { Err(NOT_PARENT_MEMBER) } — with no personal-signer fallback. Nothing about gating an event requires a new token.

reasoned: an on-chain registry earns its cost by enforcing scarcity against strangers you have no other way to reason about. Inside a squad already closed by MLS membership and roster binding, there are no strangers, so the contract solves a problem that does not exist at that scale — the same reason a two-person project does not incorporate before it has a dispute to arbitrate. Chain value appears exactly when a claim must be legible outside the closed set.

Rationale

This is the idea that changes what gets built rather than how. If two of the three jobs need no chain, then “should we ship an NFT contract” becomes “should we ship a dispute-and-export contract we almost never call” — different scope, different risk, different sequencing. It deserves an explicit decision rather than being skipped past, and it is the cheapest way to get most of issue #124’s user-visible value in the near term while the deployable chain set is still ['sepolia', 'local'].

Downsides

The income leg does not survive the headline. NIP-57 zaps require Lightning — channels, receipts, a wallet model Pacto has no infrastructure for — so “no chain at all” really means “a different chain, with its own literacy burden.” A Nostr-event claim is also only as authoritative as the relay set that carries it, and replaceable events give weaker dispute-resolution guarantees than an on-chain registry precisely where disputes matter most. Choosing this forecloses most of ideas 1 through 6, since they assume a token exists: it is a fork, not a complement.
