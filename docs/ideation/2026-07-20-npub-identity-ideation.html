Ideation artifact

Nostr npub identity & mentions in Pacto

Date: 2026-07-20
Topic: npub-identity
Mode: repo-grounded

Focus: uniquely identify a Nostr npub in Pacto to a username / profile name so that mentioning people is easy and we are talking to the correct / intended identity. User clarified: this is about tying a npub to an identity so profiles become "unique."

Grounding Context

Project shape. Pacto is a Tauri v2 desktop app (SvelteKit/Svelte 5 frontend, Rust backend). Nostr handles E2EE DMs (NIP-59 gift wraps) and MLS group messaging (kinds 443/444); EVM/Aztec handles treasury and governance. Per-account SQLite lives under each npub.

Identity model. The npub is the identity root. The same BIP-39 seed derives the Nostr keypair and the EVM wallet. Chat ids are the npub for DMs and the MLS group id for squads. Profiles are keyed by npub in a writable Svelte store; getProfileDisplayName resolves nickname → name → display_name → short npub. @ mentions already exist for squad channels: a JSON envelope {body, mentions} is encrypted inside MLS, the canonical target is the npub, the display alias is resolved from the live profile store at render time, and assignMentionAliases disambiguates duplicates by appending ·<npub prefix>.

Pain points. No global username uniqueness — Nostr display names and nicknames can collide, and the current fix is only per-squad alias disambiguation. The nip05 field is present on profiles but not surfaced as a trust signal. Display names are not self-certifying, so spoofing a familiar name is possible. There is no contact-book or petname system beyond local nickname overrides. Commons discovery shows name claims without cryptographic verification beyond the underlying npub.

Leverage points. 1) NIP-05 can bind an npub to a domain-verified handle. 2) Squad roster + MLS membership already defines a closed membership set. 3) The profiles store and getProfileDisplayName are central chokepoints for injecting verified identity badges. 4) Roster EVM binding maps (parent_id, member_npub) → EVM address, offering a second on-chain trust anchor. 5) assignMentionAliases can incorporate verified handles to reduce collisions.

Strategy. Pacto targets DAO/collective organizers who need private coordination and enforceable collective action without KYC. The core bet is that one Nostr keypair powers both private messaging and scarce on-chain actions. Active tracks: embedded treasury & governance; private group coordination via MLS squads; Discovery & Commons; Trust & safety.

Research notes. Both external web research and docs/solutions/ learnings failed in this run (credits / model selection), so all bases are repo-grounded only. Evidence dossiers are preserved in the run scratch directory.

Topic Axes

  1. Identity binding mechanisms — cryptographic or domain-verified ways to tie an npub to a unique, self-certifying handle.
  2. Mention authoring and disambiguation — how @mentions are typed, resolved, rendered, and kept unambiguous.
  3. Trust signals and verification UI — how the UI communicates identity confidence, verification status, and spoofing risk.
  4. Roster-scoped identity — using squad/MLS membership and roster EVM binding as a bounded identity namespace.
  5. Contact book and petnames — local, user-controlled naming and identity management beyond Nostr metadata.

1.

Verified NIP-05 as canonical identity anchor

Identity binding mechanisms
Confidence: 90%
Complexity: Medium
Description

Make NIP-05 a real trust anchor by fetching and caching .well-known/nostr.json verification in the Rust backend, instead of copying the claimed value from Kind 0 metadata. Treat verified NIP-05 as the canonical username everywhere, falling back to unverified metadata only when NIP-05 is absent or fails verification.

Basis

direct: src-tauri/src/profile.rs:143-148 copies meta.nip05 into the local profile without any .well-known/nostr.json validation; src/components/settings/ProfileSection.svelte:231-237 renders the claimed NIP-05 with a green checkmark, giving users false confidence that it is verified.

Rationale

Nostr display names are not unique and can be spoofed; only verified NIP-05 binds an npub to a domain-controlled identifier. Today the checkmark is decorative and actively misleading, which is the single biggest hole in identity trust.

Downsides

Requires a network fetch to the claimed domain, which complicates offline use and leaks some metadata. NIP-05 adoption is not universal, so this is a strong signal when present but not a complete solution.

Decorative NIP-05 claim becomes a verified, domain-backed handle.
2.

Roster EVM binding as canonical self-certifying handle

Identity binding mechanisms
Confidence: 85%
Complexity: Medium
Description

Use the existing squad membership and roster EVM binding as the canonical unique handle within a squad. Because (parent_id, member_npub) → EVM address is already required and fail-closed by the ACL, it gives every member a scarce, self-certifying identifier.

Basis

direct: src-tauri/src/migrations/V16__squad_member_evm.sql:1-8 stores (parent_id, member_npub, evm_address) as the primary key; src-tauri/src/evm/access_control/identity.rs:47-51 returns ACL_UNBOUND when no roster EVM is linked, proving the binding is already treated as authoritative.

Rationale

Display names and NIP-05 handles can be duplicated or lied about; an EVM address is unique and can be challenged with a signature. Anchoring identity to the roster EVM makes squad-scoped identity both unique and self-certifying.

Downsides

EVM addresses are long and hard to read. The signal is only meaningful inside a squad, so it does not solve DM or Commons identity on its own. It also ties messaging identity to on-chain actions.

3.

Squad roster as authoritative mention namespace

Mention authoring and disambiguation
Confidence: 80%
Complexity: Medium
Description

Make @mentions inside a squad strictly roster-scoped: the autocomplete candidate list is already the squad's MLS member set, and the rendered alias is resolved only from that closed set. Use the roster's existing NIP-05 / EVM bindings as the primary disambiguation key so that collisions are resolved by verified identity rather than by appending a raw npub suffix.

Basis

direct: src/lib/messaging/mentions.ts:42-64 currently deduplicates colliding aliases by appending an npub suffix; src/components/channel/ChatView.svelte:695-702 wires mentionCandidates={panelMembers}, so the squad roster is already the candidate source.

Rationale

Mention resolution becomes unambiguous by construction inside the squad, and it aligns perfectly with the ACL trust boundary. It also eliminates the risk of mentioning an external lookalike that impersonates a squad member.

Downsides

Limits mentions to roster members, which may be too restrictive for some workflows. Requires roster membership to be in sync before mentions work.

Mentions are resolved only against the closed squad roster, not the global Nostr namespace.
4.

Identity confidence badges on every name surface

Trust signals and verification UI
Confidence: 85%
Complexity: Low
Description

Add a consistent, tiny badge next to every display name across DMs, squad channels, Commons cards, and settings indicating the identity tier: verified NIP-05, roster-bound, local petname, or unverified metadata. Make the badge a single source of truth so users instantly know how much to trust a name.

Basis

direct: src/components/settings/ProfileSection.svelte:231-237 shows NIP-05 only in settings; src/components/dm/Message.svelte:1-40 renders messages with no secondary identity indicator; src/components/commons/CommonsBroadcastCard.svelte:40-44 derives the card title from unverified $profiles metadata.

Rationale

Spoofing is easy because the same display name renders identically regardless of verification status. A persistent, unified badge makes the trust boundary visible in every conversation and discovery surface. Once the badge vocabulary exists, every new identity signal automatically communicates without redesigning each screen.

Downsides

Risk of UI clutter if not carefully designed. The badge vocabulary must be legible and stable; a wrong iconography can train users to ignore it.

The same display name carries different confidence depending on the badge.
5.

Roster-scoped unique aliases / captain-gated squad petname registry

Roster-scoped identity
Confidence: 75%
Complexity: Medium
Description

Let captains assign unique, squad-shared petnames to members that are stored in a new squad_member_handle table and broadcast via MLS announcements. Unlike local nicknames, these petnames are shared across the squad so everyone sees the same name, and collisions are resolved at assignment time by the captain rather than by appending hex suffixes.

Basis

direct: src-tauri/src/profile.rs:803-818 and src/lib/api/nostr.ts:210-218 implement local-only nicknames; src-tauri/src/migrations/V16__squad_member_evm.sql uses (parent_id, member_npub) as the natural per-squad member key, so the schema pattern already exists.

Rationale

Local nicknames are powerful for the individual but useless for a group trying to agree on who "Alice" is. A captain-gated registry turns the squad roster into a shared address book with authoritative, unique names without requiring a global namespace or KYC.

Downsides

Concentrates naming power with captains; members may dislike assigned names. Requires an MLS broadcast mechanism and a new schema migration.

6.

Petname-first identity resolution

Contact book and petnames
Confidence: 90%
Complexity: Low
Description

Promote the local nickname field to the primary identity for each npub. In every rendering context—DM headers, squad messages, Commons cards, and mention autocomplete—the user's chosen petname wins over Nostr metadata. The contact book becomes the user's sovereign namespace; collisions are impossible because the user can only assign one petname per npub.

Basis

direct: src/lib/utils/profile.ts:24-32 resolves display names nickname-first; src-tauri/src/profile.rs:803-818 stores nickname independently and emits profile_nick_changed, preserving local overrides across Nostr metadata syncs.

Rationale

Global name uniqueness is a losing battle in a permissionless network. Petnames are local, user-controlled, and impossible to spoof from the outside: your "Alice" belongs to you and cannot be hijacked by someone else's metadata. This also compounds every other trust signal by letting verified badges appear next to the user's chosen name.

Downsides

Only works if users actually set petnames. A sparse contact book weakens the effect. Needs import/sync support (e.g., from Nostr follow lists) to be useful from day one.
