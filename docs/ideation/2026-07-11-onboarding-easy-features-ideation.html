Grounding Context

Grounding Summary — Onboarding Improvements for Pacto

Codebase Context

Pacto is a Tauri v2 desktop app: SvelteKit/Svelte 4 SPA frontend, Rust backend, Nostr/MLS messaging, EVM wallet from a single BIP-39 seed. Single root route src/routes/+page.svelte hosts the whole UI. Svelte 4 stores with per-npub localStorage persistence via persistenceKey. Backend uses global state (STATE, NOSTR_CLIENT, MNEMONIC_SEED, TAURI_APP, ENCRYPTION_KEY) and per-account SQLite. No public alpha shipped; greenfield posture favors breaking, minimal paths over legacy shims.

Notable patterns: src/lib/api/* typed Tauri invoke wrappers; src/lib/app/tauri-subscriptions.ts backend → UI event bridge; src/stores/auth.ts for create/import/unlock/logout; src/stores/persistence.ts for npub-scoped account state; strategy tracks in STRATEGY.md.

Obvious Pain Points / Gaps

  1. Single seed = single catastrophic loss point for both messages and money; no visible key-recovery path.
  2. Squad creation requires deploying Safe + governance + Hats on-chain, needing gas and understanding before a user can chat.
  3. Nostr/MLS concepts (npub, nsec, relays, keypackages, gift wraps, MLS welcome) leak to the user without a clear mental model.
  4. Discovery is split between Commons feed and private invite flow; no progressive onboarding into first squad.
  5. No guided first-run, empty-state education, or testnet/sandbox path.
  6. Squad invite accept rate is a top metric, suggesting the invite/join flow is already recognized as fragile.
  7. Wallet/EVM setup surfaces dense contract jargon (Hats tree, bytes32 roles, executor scopes) without plain-language UX.
  8. Account setup uses a hard-coded Argon2 salt, sessionStorage unlock flag, plaintext EVM key export, and open TODOs (random salt, pre-alpha migrations).

Leverage Points

  • Add a first-run wizard gated by an onboarding store flag in src/stores/auth.ts/persistence.ts.
  • Seed the user with a default first squad or demo Commons content so the app is not empty after account creation.
  • Use src/lib/api/nostr.ts and invite-accept flows to wrap squad joining with better error messaging and progress.
  • Add a testnet toggle for squad infra so users can practice governance before spending real gas.
  • Surface the embedded wallet in stages (receive-only, then send, then deploy).
  • Reuse the existing #personal-alerts virtual bucket for an onboarding checklist or roster-binding nudges.
  • Capitalize on the #new user/squad broadcast tag in Commons to surface first-steps prompts.

Relevant Strategy Tracks

  • Discovery & Commons (find first squads)
  • Private group coordination (make MLS Squad creation feel like Discord)
  • Trust & safety (key loss, spam)
  • Embedded treasury & governance (squad infra deployment is the biggest complexity cliff)

Past Learnings

  • Onboarding is already a strategic metric: STRATEGY.md tracks Squad invite accept rate (signals onboarding simplicity and trust), 30-day retention of new squad members, and Commons follows → squad joins.
  • Pre-public-alpha / greenfield: prefer breaking, minimal paths; remove alpha-only repair code in docs/legacy-fixes/ before beta.
  • Identity-first and cryptographic: one BIP-39 seed derives Nostr npub and all EVM accounts; users must understand npub, nsec, seed, squad-purpose vs advanced-purpose keys, and per-account SQLite isolation.
  • Governance UX ideation (2026-07-02) proposed the Nave Pirata pirate metaphor and one-click default deploy with reversible defaults to reduce contract jargon.
  • Commons auto-tags a user's first broadcast with #new and shows new squads with #new; this is a hook for onboarding/discovery but has no equivalent first-run UX inside the app.
  • Hub-channel / virtual-bucket design reserves a #personal-alerts channel for prompts to action — a natural place for an onboarding checklist or roster-binding nudges.
  • Download acquisition funnel is being rebuilt: docs/plans/2026-07-11-001-feat-download-site-landing-plan.md collapses pacto-download into pacto-app.
  • Operator checklists (docs/wallet/OPERATOR_SMOKE.md, MANUAL_E2E_CHECKLIST.md) document real onboarding steps: enabling chains, adding RPCs, importing Anvil keys, funding Sepolia, deploying sponsor → gov → Safe in order, and sharing roster EVM addresses.

External Context

  • Progressive disclosure / staged setup: surface features gradually to reduce cognitive load, but self-custodial seed backup cannot be deferred forever. Sources: userpilot.com, uxpin.com.
  • Seed-phrase backup as a safety ritual: show → write down → verify, with calm copy and honest irreversibility. Sources: medium.com, 925studios.co.
  • Empty states that teach the next action: pre-populated starter content and direct CTAs reduce blank-canvas paralysis. Sources: uxpin.com, eleken.co, userpilot.com.
  • Contextual coaching inside the workspace: tooltips and coach marks reduce doc reliance; must be skippable and keyboard-accessible. Sources: toptal.com, userpilot.com, blakecrosley.com.
  • Trust framing and legible risk: no KYC/no central authority means the UI must signal honesty and local-first operation; do not hide irreversibility. Sources: blakecrosley.com, dev.to, element.io.
  • Intent-based / branched onboarding: route users to messaging or wallet first based on self-reported intent. Sources: userpilot.com, medium.com.
  • No-KYC caveat: irrecoverability is the central constraint. Any pattern that hides or delays seed-phrase backup must still verify the user has a backup.

1

Intent-based first-run router

First-run feature orientation 85% confidence Medium complexity

After PIN setup, ask a single question about the user’s intent—e.g., join a squad, message a friend, discover public squads, or move funds. Route to the matching tab and pre-open the relevant empty-state CTA. Persist the intent to drive later coaching and progressive disclosure.

Basis: direct: src/components/layout/TopNavbar.svelte:19 exposes Commons / DMs / Squads tabs with no onboarding labels; src/routes/+page.svelte:1001 shows "Select a squad channel" as the empty state; src/components/auth/WelcomeScreen.svelte:6 only offers Create or Import. external: intent-based onboarding reduces blank-canvas paralysis.
Rationale: Pacto bundles messaging, public discovery, and treasury; forcing every user through the same default tab hides the path they actually care about.
Downsides: Requires careful design to avoid a quiz-like experience; intent may be wrong and need correction later.
2

Verified seed-backup gate with progressive enforcement

Account setup & key safety 80% confidence Medium complexity

After account creation, require users to view, write down, and verify a random subset of their 12-word recovery phrase before the main shell unlocks. A lower-friction variant allows immediate exploration but blocks receiving funds, joining squads, and exporting keys until backup is verified.

Basis: direct: src/components/auth/KeyImport.svelte:111-113 already frames the recovery phrase as "encrypted with a PIN and stored securely on this device"; src/components/auth/Login.svelte:9 ends the auth step machine at pin-unlock with no post-create backup step; src-tauri/src/lib.rs:4549 generates a 12-word BIP-39 phrase on create_account().
Rationale: Self-custody means no password reset; a verified backup is the precondition for all downstream risky actions (wallet, governance, squad ownership). The current flow silently trusts the user to back up later.
Downsides: Adds friction to first launch; must balance safety with activation; progressive-enforcement variant is more complex than a single gate.
3

Unified onboarding checklist in #personal-alerts

Contextual coaching & empty states 85% confidence Medium complexity

Convert the existing #personal-alerts virtual channel into a persistent per-user onboarding mission log: action cards for verified backup, default wallet, first squad join/create, roster signer binding, and testnet funding. Auto-advance as backend events fire; unresolved cards show badges in the sidebar.

Basis: direct: src/lib/squad/hub-channel-names.ts:8 defines PERSONAL_ALERTS_CHANNEL_NAME; docs/communities/DESIGN.md:52 reserves it for prompts to action; src/components/inbox/SquadRosterKeyInboxCard.svelte:59 already renders an action card there; src/components/channel/Channel.svelte:8,19 renders badge counts for hub rows.
Rationale: The app has no centralized onboarding surface; #personal-alerts is already an action inbox, so setup cards feel native and scalable.
Downsides: Could overload the channel if too many cards are shown; needs careful dismiss/reset behavior.
4

Invite-accept guided onboarding funnel

First squad / social activation 80% confidence Medium complexity

Turn an incoming squad invite into a short, skippable wizard that explains what a squad is, auto-creates a default squad-purpose wallet if one is missing, binds the roster signer, and deposits the user into the squad channel only after the welcome is accepted.

Basis: direct: src/components/invites/InviteCard.svelte:87 already tells the user to "Set your roster signer in the squad #personal-alerts channel"; src/lib/squad/accept-invite.ts:191-196 already calls backfillSquadMemberEvmFromProfiles after accept. STRATEGY.md tracks squad invite accept rate as a top metric.
Rationale: Squad invite accept rate is a top strategic metric; the current path is fragile and relies on the user knowing what a roster signer is.
Downsides: A wizard adds steps to an already complex flow; must be skippable for power users.
5

Solo-first personal sandbox squad

First squad / social activation 75% confidence Medium complexity

Remove the at-least-one-member requirement for a user’s first squad by auto-creating a private, single-member “My Space” squad. The user can explore channels, send messages, create polls, and simulate treasury deploys before inviting real humans.

Basis: direct: src-tauri/src/lib.rs:5437-5448 returns "Select at least one member to create a group" when member_ids.is_empty(); src/components/layout/Navbar.svelte:465 tells users "Add friends in DMs first to create a squad with them."
Rationale: Requiring a friend to be present before a user can see the squad UI is a hard activation cliff; a solo sandbox keeps them in the app and builds momentum.
Downsides: Changes the social contract of squads; may confuse users if the space is empty; backend MLS group with one member may need special handling.
6

One-click testnet treasury sandbox with faucet

Wallet & treasury activation 70% confidence High complexity

Add a persistent “Practice mode” toggle that defaults all wallet and squad deploys to local/Sepolia testnet, provides one-tap faucet links, and guides the user through the Sponsor → Pacto Gov → Safe deploy order with mock funds.

Basis: direct: docs/wallet/MANUAL_E2E_CHECKLIST.md:7-8 requires external Sepolia ETH/USDC faucets; src/components/parent/dashboard/DashboardGovernanceTab.svelte:28-31 shows "Deploy squad sponsor first"; src-tauri/src/evm/squad_sponsor_deploy.rs:44-48 rejects a zero initial deposit.
Rationale: Treasury/governance deployment is the biggest complexity cliff; a sandbox removes the fear of real loss and trains the deploy order.
Downsides: High implementation cost (faucet integration, testnet state, mock tokens); may create false confidence if testnet behavior diverges from mainnet.
7

Context-aware empty-state coach card

Contextual coaching & empty states 80% confidence Low-Medium complexity

Replace passive “No X yet” / “Select a channel” placeholders across the app with a single smart coach card that detects the next missing onboarding step and surfaces a CTA, plus a one-line “why this matters” explanation.

Basis: direct: Evidence dossier notes “No shared EmptyState primitive; empty states are duplicated across empty-state, dashboard-placeholder-text, wallet-view-empty, commons-state” and “Empty states are present but passive.”
Rationale: Dozens of empty states currently say the same thing; a unified coach card reduces duplication and gives every screen a clear next action.
Downsides: Requires a robust source-of-truth for “next onboarding step”; needs design to avoid being intrusive.
