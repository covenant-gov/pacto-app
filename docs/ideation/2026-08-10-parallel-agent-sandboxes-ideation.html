Grounding Context

PR #239 gave make dev a per-branch data dir (test_fixtures/dev-branch-<slug>), which fixed storage-format gate collisions and created this run's problem: every fresh branch sandbox boots to an empty account-creation screen. Issue #237 tracks the two remaining gaps: fixed Vite ports (1420/1421, strictPort:true) block concurrent make dev across worktrees, and fresh sandboxes carry no account, squad, DMs, or wallet state.

Codebase facts the survivors are qualified against (verified this run):

  • TRUSTED_RELAYS is a compile-time constant (src-tauri/src/lib.rs:109-119) with 25+ call sites across MLS, commons, and squad-bot paths; local-dev-setup.ts adds ws://localhost:7000 to the user relay list only — MLS traffic cannot reach the local relay at all today.
  • The launch wall is network, not crypto. Argon2id is tuned to ~100 ms (crypto.rs:39-41); the documented 20–30 s account-creation wait is relay round-trips — an MLS keypackage publish plus fetch calls with 5–15 s timeouts against public relays. The relay override is what kills the wall; skipping the interactive flow kills the choreography.
  • test_login_fixture (debug-only, PACTO_ALLOW_TEST_AUTH=1) creates an account instantly but never persists a PIN-encrypted key or emits an auth event, so the UI stays on the welcome screen (docs/TAURI_MCP_INTEGRATION.md:168). Identity adoption already ships — importAccount(recoveryPhrase, pin) at src/stores/auth.ts:250 plus a raw-nsec backend primitive — so zero-click login is automation of an existing path, not new capability.
  • pacto-dev-env runs one shared docker stack (relay :7000/:7001, Anvil :8545/:8546, bot daemon) with idempotent make seed / make seed-squad that already create identities, Safes, and governance contracts, writing full-system.json / squad.json artifacts nothing in pacto-app reads. macOS ControlCenter squats port 7000; the working endpoint is wss://localhost:7001.
  • Correction to prior grounding: pacto-bot-api bots can create MLS groups and invite members — agent.create_mls_group / agent.invite_to_mls_group (+ admin.* variants) exist at schemas/jsonrpc.json:850-971 (verified by orchestrator and independent verifier), plus pacto-bot-admin mls-group create|invite CLI verbs.
  • Correction: the MCP bridge's ipc_execute_command cannot invoke app commands; the working path is webview_execute_js → window.__TAURI__.core.invoke(...) (docs/TAURI_MCP_INTEGRATION.md:170).
  • process_rumor is pub and relay-free (rumor.rs:125-128), so synthetic history can enter storage through the real ingest path with no network. CI provisions zero fixture data across all four jobs.
  • Copied binary pacto.db fixtures remain a crypto hazard (per-device Argon2id salt + sentinel, migration.rs:15-23) and a storage-format-gate trigger — regeneration-from-code is the settled fixture policy. Likewise, MLS store bundle transfer is mechanically possible (pacto-bot-admin export/import, exact mdk 0.8.0 crate parity) but protocol-hazardous: every export is stamped split_brain_warning: true. Invitation, not transfer, is the safe default.
Reframe The seeding machinery mostly exists in the sibling repos — and is stronger than previously believed, since bots can create squads outright. What is missing is (a) one network seam (TRUSTED_RELAYS), (b) one identity seam (a shared manifest + deterministic keys), and (c) per-worktree concurrency (ports). Everything else is orchestration glue — plus a relay-free tier for CI and an on-chain artifact import, both absorbed from the 08-08 round.

External grounding (research value: high): Arcjet's per-agent workspace split (shared singleton infra, per-agent app instances), Foundry Anvil's two-tier evm_snapshot/dumpState pattern, Dagger's container-use (per-agent container on its own branch), Matrix Complement/SyTest black-box protocol suites, and the preview-environment market's consensus that seeded data is the unsolved trickiest piece. No known tool combines worktree-per-agent + seeded protocol services (relay/chain) + persona bots — the triple intersection this repo is positioned to own internally.

1 Debug-gated runtime TRUSTED_RELAYS override

Description: Replace the compile-time TRUSTED_RELAYS static with a OnceLock<Vec<String>> resolved once at startup from PACTO_TRUSTED_RELAYS (comma-separated), defaulting to today's three-relay list so all 25+ call sites read through unchanged. Gate the override on the same trust boundary the app already uses: #[cfg(debug_assertions)] plus the existing localhost-only ws:// rule (lib.rs:4554-4585) and the PACTO_ALLOW_TEST_AUTH-style env needle. Retire the seven stale ws://localhost:7000 doc references in the same pass (wss://localhost:7001 is the working endpoint).

Axis
network-seam
Basis
direct: src-tauri/src/lib.rs:109-119 (pub(crate) static TRUSTED_RELAYS: &[&str]) with 25+ call sites enumerated in the evidence dossier; lib.rs:4554-4585 already restricts plain ws:// to localhost; operator_env (dotenvy) already loads a repo-root .env into process env in debug builds — the delivery mechanism exists.
Rationale
The keystone: no seeded sandbox, bot persona, or CI scenario can round-trip MLS (keypackages, welcomes, group messages) locally while MLS traffic is pinned to production relays. And since the 20–30 s launch wall is relay round-trips, not crypto, this override is also the change that makes sandbox boot fast. Every other idea on this list is capped by this constant. It is also a safety fix — today a "local" sandbox silently talks to production relays.
Downsides
Security-relevant boundary change: widening what a debug build's core protocol can talk to needs explicit review of the gating (env var + debug_assertions + localhost-only). Must not leak into release builds.

2 Born-populated sandboxes: invite-first, bot-created squads, one-command bootstrap

Description: Sandboxes are never created empty, and nothing is ever copied — the developer (or agent) is invited into a world the bots build. A single make dev-world: brings up the shared pacto-dev-env stack with real readiness gates between stages (up → seed → keypackages → handoff → launch), provisions the branch's app identity, then has a seed bot create the squad via agent.create_mls_group and invite the sandbox account via agent.invite_to_mls_group — with persona bots posting history after the invite (MLS forward secrecy means a new member cannot read pre-join messages), so first paint shows a lived-in squad with a counterparty that replies.

Step zero — the free experiment: the bot roster already publishes to wss://jskitty.cat/nostr, which is in the app's default TRUSTED_RELAYS. So pacto-bot-admin mls-group invite --recipient <DEV_NPUB> can put a populated squad in front of a stock debug build today, before any code lands — the cheapest way to validate the whole invite-first design (at the cost of briefly pushing dev traffic over a public relay; not the steady state).

Axis
sandbox-lifecycle
Basis
direct: agent.create_mls_group / agent.invite_to_mls_group verified at pacto-bot-api/schemas/jsonrpc.json:850-971; CLI mls-group invite --bot --group --recipient at admin.rs:605-618; seed-squad.sh already creates captain/candidate/crew identities and Safes; auto-hello_message on mls_welcome_received (docs/python-sdk-squad-bots.md:160-180); issue #237 acceptance criterion 2 verbatim. reasoned: MLS binds membership to a client's own key material — a Welcome-derived member gets its own ratchet, so invitation is hazard-free by construction, whereas any store-copy path carries the split_brain_warning: true hazard bot-api itself stamps on every export.
Rationale
The literal user ask — "predefined users with populated data" — via the only path in the design space that is hazard-free by construction rather than hazard-managed. The verified create_mls_group RPC makes it cheaper than the 08-08 round assumed: no app-side squad-creation choreography at all. Depends on idea 1 for local MLS; step zero doesn't.
Downsides
Largest orchestration surface (three repos, one command); cross-repo ownership must be decided (does pacto-app's Makefile shell into siblings, or does pacto-dev-env own the verb?); must degrade gracefully to today's make dev on machines without Docker; invitation grants membership, not history — the backlog step is mandatory, not optional.

3 Deterministic per-worktree ports from the branch slug

Description: Hash the branch slug that make dev already computes for PACTO_TEST_SANDBOX_ROOT (Makefile:47-56) into a stable port offset (e.g. 1420 + 2·(hash mod N)), export it as PACTO_DEV_PORT, and thread it through vite.config.ts (read env instead of literal 1420/1421) and the Tauri dev URL (config override / --config merge at dev time). No human ever picks a port; no two worktrees collide; main keeps 1420.

Axis
sandbox-lifecycle
Basis
direct: vite.config.ts:55-65 (port:1420, strictPort:true, HMR 1421), tauri.conf.json:8 (devUrl literal); issue #237 problem statement 1 ("two make dev processes can't run concurrently"); the slug-derivation pattern is already trusted for the data dir in the same Makefile target.
Rationale
The cheapest change on this list and the hard precondition for "parallel" in parallel-agent workflows: without it, N agents in N worktrees is structurally impossible regardless of how good seeding gets. Deterministic (not first-free) allocation means an agent can reconnect to its own instance by recomputing the port from its branch.
Downsides
Hash collisions possible on a small port range (mitigate with a wider range or collision fallback); Tauri devUrl templating needs a small wrapper or --config merge since tauri.conf.json is static JSON.

4 Zero-click authenticated boot: finish test_login_fixture

Description: Extend the debug-only test_login_fixture to accept a supplied identity (nsec or manifest-referenced mnemonic, instead of always generating a random one), persist a real PIN-encrypted key via the same encrypt/migration::encrypt_with_password path real PIN creation uses (dev PIN 123456), and emit the auth event checkAuthStatus() listens for — so a sandbox launch (or one webview_execute_js → invoke call) lands directly in an authenticated UI. Kills the per-verification choreography every MCP-driven agent pays today: 3 DOM snapshots + 12 single-digit keypress calls.

Axis
agent-safety
Basis
direct: docs/TAURI_MCP_INTEGRATION.md:168 ("never emits an event or triggers a reload… never persists a normal PIN-encrypted key for checkAuthStatus() to find"); lib.rs:6091-6150 verified to skip the encrypt path; importAccount(recoveryPhrase, pin) already ships at auth.ts:250, so this automates an existing capability rather than adding one; delivery constraint verified at TAURI_MCP_INTEGRATION.md:170 (ipc_execute_command can't call app commands — use the documented execute_js invoke helper).

AGENTS.md mandates MCP verification for every UI change, so the choreography multiplies linearly with agent count and change count. Note the honest scope: Argon2id itself is ~100 ms — the 20–30 s wall is relay timeouts, which idea 1 removes; this idea removes the interactive gate and the fragile scripted flow. Composes with idea 2: the one-command boot needs exactly this to end authenticated, as the supplied-nsec input is the manifest handoff.
Downsides

5 world-state.json manifest + germ-line key derivation

Description: One canonical, versioned manifest schema — {persona, npub, nsec_env_ref, eth_address, bot_id, squad_role, mnemonic?} — written by seed-squad.sh, consumed by pacto-bot-api.toml generation and by a pacto-app fixture loader (idea 4's supplied-identity input). All dev identities derive from one dev root seed via role-keyed HKDF/BIP-32 derivation instead of Keys::generate(), so the whole cast regenerates byte-identically anywhere. Commit the small derivation recipe (the germ line); always regenerate derived state — encrypted keys, SQLite DBs — fresh per machine (the disposable soma). Nothing binary is ever committed.

Open design fork: HKDF determinism vs bunker custody

The 08-08 round proposed the opposite identity philosophy: mint personas with pacto-bot-admin new --backend bunker_local (NIP-46), so no private key is ever written to a config, env var, or script — the dev stack already runs a nip46-bunker container, and test-bunker verifies connections. Bunker custody removes the secret copy entirely but adds a live signing dependency (offline dev breaks confusingly) and exercises a NIP-46 path the desktop app may not fully support yet. Position taken here: HKDF-deterministic keys now (reproducibility and diffability are what parallel agents and CI need), bunker as the eventual hardening default once app-side NIP-46 support is confirmed. This is a decision the team should ratify, not a settled fact.

Axis
seeded-identities
Basis
direct: three independent identity shapes exist today (seed-squad.sh:596-598 crewMembers JSON, pacto-bot-api.toml.example [[bots]], app-side mnemonic import at lib.rs:6226); signer.rs:432 uses random Keys::generate(); per-device salt/sentinel (migration.rs:15-23) is why binary fixtures can't be shared; bunker backend verified at admin.rs:274-277 with test-bunker at admin.rs:379-384. reasoned: the germ-line/soma split (store the reproducible pre-image, regenerate instances) is the only fixture policy that is simultaneously safe, portable, and diffable.
Rationale
The compounding foundation: once identities are deterministic and manifest-described, ideas 2, 4, 6, 7, and 9 all consume the same artifact instead of re-inventing identity plumbing per repo — and "which user am I logged in as in this sandbox?" has one answer across all three codebases.
Downsides
Cross-repo schema ownership must be settled (versioning, breaking changes); touching bot-api's key generation is security-adjacent and needs review; derivation must be clearly dev-only; the bunker fork stays open until app NIP-46 support is checked.

6 Persona cast + scenario driver doubling as an MLS conformance suite

Description: Package the existing Bot SDK surface (@bot.on_squad_join, hello_message, @bot.command, throttles) into a library of pre-rehearsed persona roles — Captain, Skeptical Candidate, Chatty Crew, Governance Objector — selectable at launch (make dev-world PERSONA=captain-with-treasury, crew-with-dm-backlog, candidate-mid-vote; map dev-account/dev-buddy onto specific roster members so two windows hold a genuine two-party conversation). Declarative scenario files name participants and a timeline (t+0 captain DMs the dev; t+5m creates "council"; t+10m crew-1 posts three messages; t+15m a poll opens) and compile to real JSON-RPC verbs against the live local relay + Anvil. The same scenarios run in CI as a Complement-style black-box multi-party MLS regression gate, with trace-events output snapshotted as golden files so a scenario that silently stops producing what it claims fails loudly.

Axis
personas
Basis
direct: full RPC surface verified including agent.create_mls_group/invite_to_mls_group (jsonrpc.json:850-971); shell-composable primitives send-test-dm, mls-group create|invite, publish-profile, trace-events --since --limit (admin.rs:374-461, 584-618); new --scaffold generates a pytest project (admin.rs:294-308) — the scenario can live as the SDK's own test and cannot drift from its API; python-llm cookiecutter template as packaging vehicle. external: Matrix Complement/SyTest — black-box suites driving real homeservers catch integration bugs mocked-internal tests structurally cannot; the analogy holds (E2EE protocol correctness is only observable over the wire).
Rationale
Turns seeding investment into a second dividend: MLS group messaging currently has no automated multi-party regression coverage, and every scenario written to make sandboxes lively is also a protocol test for free. Scenario-driven state is genuinely cryptographic — something a row-inserting seed script can never produce for MLS. Converts "we have bots" into "we have a cast": a shared asset that compounds instead of bespoke one-off configs.
Downsides
A scenario format is a small language — keep it declarative, resist Turing-completeness; personas are a maintenance surface (cap at three or four deliberately chosen states, each with an owner); wall-clock timelines must be simulated; CI budget and relay-timing flakiness need engineering. Needs ideas 1 and 5 first.

7 Auto-import the Anvil deployment artifacts, with version pinning

Description: The dev stack already writes real local-chain addresses to full-system.json and squad.json; nothing in pacto-app reads them. Have the dev build import those artifacts at launch to populate the existing local (31337) chain entry and treasury addresses, deleting the manual Settings → EVM step. Stamp each deployment with an accession id the app checks, so a stale or mismatched artifact (an Anvil instance whose contracts no longer match the running build's ABI) refuses loudly instead of silently resolving wrong addresses.

Axis
network-seam
Basis
direct: wallet-assets.json carries a local (31337 → http://localhost:8545) entry with zero-address placeholders; pacto-protocol-addresses.json holds only Sepolia; local-dev-setup.ts explicitly opts out of wiring EVM, leaving it a manual step; the artifacts are written to data/deployments/31337/ by the already-idempotent make seed. external: versioned reference assemblies in genomics (GRCh37/GRCh38), where tooling refuses to mix coordinate systems rather than silently producing wrong results.
Rationale
A fully populated artifact sits on disk beside a config file with matching empty fields — an existing bridge with nobody walking across it. Cheapest item on the list after ports, and it completes the world: ideas 1–6 populate the social world, this populates the on-chain one. The pinning half mirrors the storage-format gate philosophy the repo already trusts.
Downsides
Takes on a cross-repo dependency on an artifact format the other repo owns; needs defined behavior when the artifact is absent, stale, or from a wiped chain; an unchecked version stamp is worse than none.

9 Parallel-agent guardrails: doctor, leases, throwaway squads

Description: Three rails that make N concurrent agents safe by construction rather than by policy: (a) a make doctor/launch preflight that validates each sandbox root's schema version against the current build and auto-quarantines stale sandbox profiles (replacing the 5-step manual sqlite3 runbook for fixture data), and refuses launch if PACTO_TEST_SANDBOX_ROOT resolves outside the current worktree; (b) a lease file checked by reseed/seed-squad so parallel agents can't clobber shared Anvil/relay state mid-scenario; (c) every sandbox gets its own throwaway squad (from idea 2), so "don't post in production channels" stops being a judgment call — the only channels an agent can see are its own.

Axis
agent-safety
Basis
direct: OPERATOR_UPDATES.md:156 ("one bad profile blocks every account on that machine"), :158-171 (manual sqlite3 recovery runbook), :173 (branch-hopping isolation doesn't cover all triggers); AGENTS.md:282 (channel safety currently rests on agent judgment); seed-squad.sh idempotence implies concurrent-mutation risk was already anticipated.
Rationale
Parallelism multiplies exactly the failure modes these gates exist to catch, while multiplying blast radius (one agent's stale sandbox blocks every agent's account; one agent's reseed corrupts every agent's scenario). Unattended agents cannot execute manual runbooks — recovery must be mechanical or parallel workflows stall on the first incident.
Downsides
Auto-quarantine trades manual-but-safe for automatic-but-riskier — scope it strictly to sandbox/fixture profiles, never the real OS-data account; lease semantics (timeout, stealing) need care to avoid deadlocking CI.

10 Adversarial fixtures that exercise the safety rails

Description: A second fixture target that deliberately seeds hostile state rather than a plausible inbox: an Unrecognized-format profile sitting beside a valid one, orphaned rows with no matching event, and enough profiles to actually reach SCAN_DEADLINE. Pair it with a checksum over the resulting logical state so a regenerated fixture that silently diverges is caught as a desync rather than discovered later through an unrelated failure. The proving ground for idea 9's doctor/quarantine rails.

Axis
agent-safety
Basis
direct: AccountScanVerdict never returns Delete for an Unrecognized/Divergent profile (regression tests at account_manager.rs:352-382,812-830); SCAN_DEADLINE is a real 5 s bound at storage_format.rs:23 no realistic profile count has approached. external: lockstep/rollback netcode computes periodic state checksums because replay divergence is silent and catastrophic otherwise.
Rationale
Different in kind from every other survivor: PR #239 exists because of storage-format collisions, and the safety code written in response has never been exercised by a fixture that triggers it. A realistic populated user never runs those paths; only a deliberately hostile one does. With auto-quarantine (idea 9) in the design, a fixture proving quarantine fires correctly stops being nice-to-have and becomes the test for a new automated behavior.
Downsides
Serves testing rather than the daily DX complaint, so it competes for effort without making anyone's make dev nicer; the checksum half only earns its keep once fixtures regenerate often enough to drift. Build after idea 9, alongside it.
